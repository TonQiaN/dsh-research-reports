00 · 先看结论

这不是一套写作规范，而是一台维持记忆的机器

如果只带走一句话：DeepSeek Harness 的文档治理，是在「代码主要由 agent 写、每天几十个 session 并行、人类只能审不能全读」的前提下，为了让仓库自己记得自己是什么、为什么这样，而演化出来的一组机械约束。

它由五个相互咬合的部件组成，每一个都能在 git 里找到「出生证明」：

  1. 一份每个 session 都会加载的「常令」（根 AGENTS.md，CLAUDE.md 是它的 symlink），被字数上限硬卡在 1,900 词，每条规则一到三行加一个链接。
  2. 一棵用路径编码状态的决策记录树（.agents/notes/{proposed,implemented,rejected}/{class}/yyyy-mm-dd-topic.md），「非平凡改动必须带一份」，配一套哈希封印的冻结归档。
  3. 28 个退出码非零的 gate（pnpm run doc-sync），管链接、锚点、每段一行、字数、格式、双语一致、生成物新鲜、JSDoc 完整。
  4. 一张「每个事实只有一个家」的分层表和一份 9 条的 slop checklist，专门对付 agent 生成文本的两类污染：重复叙述与「泄漏的推理坐标」。
  5. 一组给 agent 用的 skill（文档标准、写作标准、去推理泄漏、归档、翻译、pre-push 选检查、code review），承载「流程与判断」，而契约留在文档里。

对你最重要的三个反直觉发现

  • 规则不是被「写好」的，是被「压出来」的：根 AGENTS.md 三周内从 52 词膨胀到 8,619 词，团队的解法不是提醒大家克制，而是先装一个 wc -w 上限 gate、再在同一天重写到 1,495 词。
  • 最强的规则往往没有 gate：「非平凡改动必须带 Agent Note」明确写着「靠 review 裁决，无自动 gate」，遵守率仍从 75% 升到 93%——但也在最关键的公开发布 PR 上失守了一次。
  • 治理本身是要付税的：约每 25–45 个提交就有 1 个纯粹为了让文档 gate 变绿；gate 代码 13.8k 行、占产品源码 9%；每次 merge master 回特性分支，都可能多付一个「重新生成目录」的提交。
01 · 元规则

第 2 天写下的一句话，此后 60 天都在给它加叶子

仓库 2026-06-10 初始化，06-11 就回填了 7 份 ADR。其中 ADR 0007 定下了整套治理的前提：

"This codebase is developed primarily by coding agents. Agents follow enforced gates far more reliably than prose conventions, and "a lot of work" is not a cost argument when agents do the labor."docs/adr/0007-quality-gates.md @ 9b8fccc6f9（2026-06-11），现位于 .agents/notes/implemented/process/2026-06-11-quality-gates.md:11

这句话有三个推论，后面每一节都是它的实例：

  • 能机械判定的都做成命令。「一段一行」不是风格建议，是 verify-md-wrap；「链接别断」是 verify-md-links；「别写太长」是 verify-doc-budgets。06-20 的分类 note 说得更直白：a convention that isn't machine-checked rots。
  • 不能机械判定的，诚实地交给 review，别假装有 gate。「什么算非平凡改动」「翻译质量是否好」「note 是否描述了 shipped reality」都明确写着「Review enforces the semantic boundary」。
  • 「工作量大」不是反对理由。三件套双语、每篇 note 一千词、每次 merge 后重新生成目录——这些在人手时代不可接受的成本，在 agent 干活时被接受了。代价见第 10 节。

03 · 常令文件

根 AGENTS.md 的新陈代谢：膨胀、重写、被上限钉住

这份文件（CLAUDE.md 从第一天起就是它的 symlink，.claude/skills 也 symlink 到 .agents/skills）是唯一「每个 session 都进上下文」的文本。它的字数曲线是整个治理史最好的缩影。

膨胀期的内容是什么？

不是坏内容，是放错了地方的好内容。06-29 版本里有一整节「Orchestrating review feedback across a stacked PR chain」，写着 "Delegated work is trust-but-verify. When sub-agents implement fixes in parallel, their report describes what they INTENDED, not necessarily what landed."；07-03 版本加了「Landing changes cleanly: gates, Codex, and scope」，记录一次 850 秒超时的收敛 prompt。这些是团队协作的真实教训——但它们是 war story，属于 cookbook 和 postmortem，不属于每次会话都要加载的常令。07-04 重写把它们搬到了 docs/cookbook/responding-to-pr-review-on-a-stack.md、新建的 docs/testing.md（预算 800）和 docs/defensive-patterns.md（预算 550）。

重写之后它长什么样

9 个 section 的骨架自 07-04 起没变过（唯一例外是 07-10~07-20 短暂存在过的「Agent efficiency」）：Pre-release stance / Repository layout / Commands / Secrets / Conventions / Defensive patterns / Type safety and documentation / Editing these instructions / Vendoring policy。Conventions 30 条占全文 42%。三段最能反映「人机协作现实」的规则，全都能追溯到某次 agent 犯错：

Host sandbox failures

Hypatia May 07-15 经 codex/document-host-sandbox-retries 分支加入：agent 被自己的沙箱挡住 gh/pnpm/网络时，会误诊为鉴权或项目故障然后去「修」代码。规则要求 "retry unchanged with the narrowest host escalation" 且 "never bypass … the product sandbox under test"。这是根文件里唯一以 agent 为主语的操作规则。

Never default to the full suite

25 天内翻转 5 次：06-29「PR ready 前跑完整 CI 序列」（问题：漏跑）→ 07-22「跑相关检查」（问题：反射性全跑、重复跑）→ 07-23 又加回又 revert。最终把「选哪些检查」外包给 dsh-pre-push-checks skill，根文件只留原则。

Trust TypeScript / Do not comment on obvious facts / Do not use metaphors

07-19、08-12、08-09 加入，全是对 LLM 文风与过度防御倾向的直接矫正：别给静态类型已保证的值加运行时校验，别写代码已表达的注释，写 contract/boundary/shape 前先问有没有更准的词。

Pre-release stance（自毁条款）

06-19 起写着 "Remove this section at the first tagged release. With no external consumers…"。08-13 dsh 家族已 0.1.0-rc.5 公开发布、221 个包设为 public，但本地 0 个 git tag，条款仍在。触发条件靠人记得，就会像这样悬着。

04 · 决策记录

从 ADR 到 Agent Notes：六次形态变化，每次都因为一个新痛点

决策记录制度不是一次设计出来的。两个月里改了六次形态，每一次的「为什么」都写在 commit 或 note 里，全部可考。

  • 06-11docs/adr/0001–0018（编号 ADR）+ docs/rfc/001–009（编号 RFC）回填。README 已有两条最稳定的不变量：写 ADR 只当决策「durable, contested, and surprising」；ADR 从不被编辑成另一个决策，只能 supersede。9b8fccc6f9、4dafad4db6
  • 06-18合并为 docs/rfc/{proposed,implemented,rejected}/，文件名改成 yyyy-mm-dd-topic.md，「ADR NNNN」裸编号引用全部改为相对链接——同一 commit 引入 verify-md-links，因为这次重组手改了约 40 条链接却没有任何检测。这是「为什么不用 ADR 编号」的可考证答案：编号无法被 lint 检查，相对链接可以，并且在文件跨目录移动时存活。7c400e9c02；2026-06-18-markdown-cross-link-lint.md ## Problem
  • 06-20加第二轴：6 个 class 子目录（feature / bug-fix / simplification / architecture / process / testing）。刻意没有 refactor（与 simplification 的判别式「observable behavior 是否改变」重叠）；拒绝在文件里加 Classification: 行——「路径已经承载的事实不再复制进文件」。605587e79c；2026-06-20-agent-note-classification.md

几条值得抄的设计

  • 路径即状态。lifecycle 与 class 都在路径里，ls 就能回答「这个决策现在什么状态」；Status: 行作为自描述冗余保留，但由 gate 与目录交叉校验。gate 里硬编码了 INDEX.md — centralized Agent Note indexes are forbidden，把被否决的方案物理封死。
  • Alternatives 强制，但只许记录、不许编造。「A decision recorded without what it beat invites re-litigation」；07-05 之前的旧 note 若回忆不起替代方案，只能放一行 <!-- agent-note-format: alternatives-not-recorded (pre-format Agent Note) -->。这是对 LLM 事后补写 rationale 倾向最便宜的防御——宁可留诚实的空洞。
  • implemented note 与现实同步，但决策本身不改。只改事实（路径、默认值、机制），原地重写不追加历史；要改决策就写新 note 交叉链接。
  • rejected 是护栏不是垃圾桶。现存 11 份，典型如 builtin-timer-promises-for-hand-rolled-sleeps：提案期 Risks 写「Essentially none」，实现 PR #679 才发现 vitest fake clock 不拦截 node:timers/promises；Status 行记录 "implementation falsified the parity premise"。实现是最好的证伪器。
  • 不进 PR 模板。.github/pull_request_template.md 里没有 note 字样；制度靠根 AGENTS.md 常令 + dsh-code-review skill 的检查项执行，与「主要由 agent 提 PR」的现实匹配。

gate 的三个共同设计语言

  • 错误消息带修复指令。几乎每条失败输出都是「下一步做什么」：run X --write、see docs/i18n/README.md、join NO_LIMITATIONS with a reason。这是给 agent 读的 gate：让它能自我修复。

  • 误伤时换更精确的解析器，不加 ignore 注释。verify-md-wrap 引入当天就从正则改成 mdast AST；verify-md-links 从「目标存在」升级到「锚点存在」时，用语料本身的 15 处修复作为红→绿证据。

11 · 学习路线

给从个人 vibecoding 走向团队的你：抄什么、别抄什么、先做什么

这个仓库的规模（15+ 人、每周数千提交、两种 agent 并行）决定了它的复杂度。你不需要它的 28 个 gate，你需要它的顺序和元规则。按你团队的大小选一列。

你一个人 + agent（现在）

先建「记忆」，不建「治理」

  • 第一天：CLAUDE.md → AGENTS.md symlink（或反之），一份真文件多个入口名。
  • AGENTS.md 里每条规则一到三行；先允许它膨胀几周收集教训，但在某个点做一次 07-04 式的重写，并加一行 wc -w 上限（1,200–1,500 词起步）到 CI 或 pre-commit。
  • 建一个 docs/decisions/yyyy-mm-dd-topic.md 目录，格式抄四段：Problem / Decision / Alternatives considered / Consequences。不编号，用相对链接。哪怕只有你一个人，Alternatives 也要写——你两周后的自己就是那个「不同的人」。
  • 把「agent 会犯的错」写成一句话规则而不是抱怨：只汇报真正跑过的命令；沙箱阻断不是项目故障；别给静态类型已保证的值加运行时校验；别写代码已表达的注释；别在文档里写 (decision 3) 这种只有当前会话看得懂的坐标。
  • 直接搬两个 skill：dsh-trim-cot-leakage（0 条仓库命令）和 dsh-prose-standard，改名后当作 AGENTS.md 的写作附录。
2–5 人

加最便宜的 gate，按仓库自己的采纳顺序

  • 依次：verify-md-links（216 行 + spec）→ verify-md-wrap（85 行）→ verify-doc-budgets（58 行 + 一个 JSON manifest，只列 2–3 份 standing docs）→ 决策记录三件（路径闭集 + 格式，~200 行）。每一步都等对应痛点出现再加。全部只依赖 mdast 与 tsx，仓库假设都在文件头的 PATTERNS 里，一小时能跑起来。
  • 指定唯一的 AGENTS.md owner；其他人经小 PR 提议；错了快速 revert。合并冲突是规则消失的盲区——多人并行改 AGENTS.md 时合并后 grep 自己的段落。
  • 本地 hook 只做秒级检查（staged lint、whitespace），全套交 CI；如果 CI 不完整，反而保留「PR ready 前跑一次全量」（仓库 06-29 版本），别照搬 "Never default to the full suite"。
  • postmortem 只在 subtle + systemic + costly 时写，固定 Executive summary + Guardrails 结构；每次事故至少改一条常设规则或加一个 gate；专门记录「agent 把什么当成了成功证据」。
  • rejected 记录当护栏不当档案：一个 REJECTED.md 维护 5–10 条，每条一行判决，每季度删过时的。
  • 不做双语，除非有两类真实读者。
5–10 人及以上

这时才值得复制它的制度层

  • 决策记录树 proposed/implemented/rejected + 「非平凡改动同 PR 带一份」；先靠 owner 以身作则再立规（仓库强制前已 74%）；强制与退出机制（archive）同一周上线，否则两周内语料翻三倍。
  • 任何中心化清单文件（INDEX、CHANGELOG、目录表）在 ≥5 并行分支/天时是冲突源，生成它也没用（gen-rfc-index 只活了 15 天）；把元数据编进路径。
  • 用 skill 承载工作流与判断标准，用 docs 承载契约；给 skill 显式触发策略（哪些只许人手动触发），多 agent 工具并存时用脚本校验策略一致。
  • review 清单里显式写针对 agent 的检查项（新 prose 语义审查、note 是否改写为 shipped reality、performative agreement）；把 reviewer 定义为 gate 看不见的语义缺陷的最后防线；人类 review 意见要有「蒸馏进 skill」的正式出口。
  • 预算给 target 与 ceiling 双值，抬 ceiling 必须在 PR 里说理由；接受 ceiling 会被反复 rubber-stamp 的现实，每两周做一次「trim」而不是靠 gate 触发。
  • 并行开发者 ≥3 且做双语时，才值得写 .i18n.yaml merge driver。

不该抄的（至少现在不该）

  • 30 条 Conventions + 5 个子树 AGENTS.md + 11 个 skill 的规模：照抄会让 agent 上下文里塞满不适用的规则。
  • 每周谈判 ceiling（66 次抬升、最小 1 词）与 73 次 manifest 提交——这是多人并发的摩擦成本；小团队一个固定上限 + 季度 review。
  • 档三的 7 个 gen-*（~6,400 行）和 verify-package-readme-model-experience（553 行、126 条 allowlist）：从源码生成参考手册、要求每个包写「模型看到什么 / token 效应 / KV cache 效应」是 harness 特有问题。
  • 生成物嵌源码行号 + 人工翻译生成物：仓库自己 64% 的返工来自这里。若做生成 catalog，让 gate 忽略行号漂移或把 regenerate 做成 pre-commit 自动步骤；生成物英文单语。
  • 带自毁条件的段落（"remove at first tagged release"）若没人负责触发，会像仓库一样在公开 rc 发布后仍挂着；要么不写，要么绑一个可机检的触发器（有 tag 则 fail）。
  • 文风词义辨析（contract/boundary/shape、reserve seam）：那是针对已积累数万行 LLM prose 的矫正；你先写清「不叙述控制流、不写变更历史」两句就够。

五个最值得带走的元教训

  • 规则 = 一条退出码非零的命令，否则它会烂。写不成命令的规则，诚实地标注「靠 review」，别假装有 gate。
  • gate 出生要附带可计数的 Problem（40 条链接、203 个导出、15 个锚点、8,130 词）。写不出数字的 gate 大概率是过早的。
  • 预算不是让文件变短，是让「加字」成为需要显式解释的行为。它成功触发了两次瘦身，但日常方向是蠕升；真正把文件变短的是人手重写。
  • agent 天然朝「更紧、更少、删掉」推，人要预设否决权并写成文字：「删字数前先列出段落里的每个命题」「删除改冻结」「Alternatives 只许记录不许编造」。
  • 历史与现状分离：其他文档一律只写现状，历史叙事集中到 postmortem 与决策记录两处，这样哪怕不写 gate，也能靠 grep 'previously|now|no longer' 做审计。

第一周可以做的事（按顺序）

  1. 建 AGENTS.md，CLAUDE.md symlink 它；写下你已经知道的 5–10 条 agent 常犯错，每条一到三行。
  2. 建 docs/decisions/，把上周做过的两个技术决定用四段模板补写，包括当时放弃的方案。
  3. 加一个 30 行脚本：检查 Markdown 相对链接是否存在（可以直接从 scripts/verify-md-links.ts 裁）；接进 CI。
  4. 给 AGENTS.md 设 wc -w 上限并写进同一个脚本；超了先搬家再压缩再抬。
  5. 把 dsh-trim-cot-leakage 的「唯一测试」和 8 类清单抄进 AGENTS.md 的写作附录，让 agent 提 PR 前自查一遍。
  6. 下一次出「CI 绿了但产品坏了」的事故时，写第一篇 postmortem，并至少改一条常设规则。
