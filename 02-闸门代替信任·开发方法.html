开发方法研究 deepseek-harness 12,293 次提交 / 64 天 快照 47f9438

闸门代替信任

DeepSeek 团队用 AI agent 在 64 天里写出了 219 个包、22.7 万行源码。这份报告只回答三个问题：用了什么工具、人和 agent 怎么分工、以及什么在兜底。结论和「vibe coding」这个词基本相反——他们在仓库的第二天就把相反的判断写进了记录，然后花 64 天把它做成了 62 条会返回非零退出码的命令。

这套方法可以用一句话概括：凡是团队做出的承诺，要么有一条在它被违反时失败的命令，要么在记录里明确写下「这条由评审负责」。

后半句和前半句一样被严格执行——有一篇 Agent Note 里就直接写着「Coverage gap: no gate rejects a new ordinal citation — review owns the rule.」

机器把关

存在一条命令，承诺被违反时它返回非零。62 条闸门、14 个聚合、每次 PR 跑。

评审负责

明确记录为无法机检，交给人。不是遗漏，是写下来的分工。

已命名的洞

团队自己点名了这个失效模式，提出了对策，而对策至今没做。

03 · 协作机制

协作的真正难题不是分工，是记忆

agent 会话是无状态的。团队规模又小(27 个可辨识的人，头部一人占 42.6% 的提交)。于是这套流程里最大的一块投入，是让上一个会话的判断能被下一个会话继承。

机制规模解决的问题

69.9 万英文词		 决策记录。按 {生命周期}/{类别}/日期-主题.md 组织，格式由闸门强制。4,591 次提交(37%)碰过这个目录;65% 的代码 PR 带着一篇。

13,578 词		 把重复工作流固化成可调用的东西。11 个里有 7 个开头就自我限定「guidance, not a script/checklist」。

Agent Note 的设计里有三处很少见的判断。

一、强制记录「它打败了什么」。每篇都必须有 Alternatives considered(541 篇活跃笔记里 526 篇有，其余 15 篇带着 2026-07-05 之前的祖父条款注释)。理由是一句很锋利的话：

A decision recorded without what it beat invites re-litigation — the failure Agent Notes exist to prevent.

.agents/notes/README.md · 另有一句：Alternatives are recorded, never invented.

二、禁止建索引。没有 INDEX.md，只能按目录树浏览或全仓搜索——理由是索引会变成合并热点，而且它重复了路径已经编码的事实。

三、笔记不能被改成另一个决定。要推翻就新写一篇并互相链接。全量取代要合并进新主并删掉旧三元组；部分取代则两篇都留，在 ## Problem 上方加一行横幅点明哪些条款已死(目前有 11 篇带这种横幅)。归档后永久冻结，而且所有文档闸门都排除归档源——这样演进中的标准永远不会产生「去改历史」的压力。

机器把关

三条闸门守着这套记忆：verify-agent-note-format(逐生命周期的文内骨架)、verify-agent-note-classification(路径编码的封闭集合，并拒绝根 INDEX.md)、verify-archived-agent-notes(归档的 sha256 追加式封条)。格式能撑过 agent 换人，不依赖谁记得住。

评审负责

但「这次改动算不算非平凡、需不需要写笔记」刻意没有闸门：Review enforces the semantic boundary. No automated gate attempts to classify a diff as trivial or non-trivial. 同理，一篇笔记的 Alternatives considered 里写的是不是真实考虑过的方案，闸门看不出来。

规则本身只有一行，在根 AGENTS.md 里：拆分独立改动；在引入问题的那个 PR 上修；重写用 --force-with-lease，远端一动就中止，永不用裸 --force。配套的 cookbook 把并行的纪律讲得更具体：

One worktree per PR branch. Each PR's fixes happen in that PR's own worktree; parallel fixes never share a checkout.

05 · 三态

把关体系：按成本分层，而不是按重要性分层

值得注意的是分层依据。本地钩子只抓「便宜且高置信」的缺陷，重活全部推给 CI，而分支保护只认两个状态检查。

This codebase is developed primarily by coding agents. Agents follow enforced gates far more reliably than prose conventions, and "a lot of work" is not a cost argument when agents do the labor.

.agents/notes/implemented/process/2026-06-11-quality-gates.md — 写于第 2 天

这段话里的经济学是整套方法的支点。一旦劳动便宜、注意力变成稀缺资源，所有人类团队会以「太贵」否掉的做法就都变得合理了：每文件 100% 覆盖率、每个包一个 invariant 伴生文件、936 对文档带哈希侧车、686 篇决策记录每篇都要写被否方案、9 份文档设字数上限。团队不是在用工作量换质量，而是在用免费的工作量换另一样东西——合并没有人通读过的代码的能力。

同一篇记录还给出了这套体系的早期动因：没通过类型检查的测试曾经就那么合进去了(vitest 不做类型检查)，只有一次评审抓住了它。

另一条同样重要的规则：别浪费注意力

根 AGENTS.md 里明确禁止 agent 反射式地跑全套：Never default to the full suite or repeat a passing check for commit or push. pre-push skill 更进一步，把所有「伪造证据」的捷径逐条封死——不许用 --passWithNoTests、不许调低覆盖率阈值、不许收窄 --coverage.include 来藏掉一个没覆盖的文件、不许「命令成功了就宣布 stack 就绪」，以及最直接的一句：

Do not push and hope CI differs.

06 · docs/postmortem · 4 份

四份复盘，四次同一个失败

四份事后复盘全部是在闸门全绿的情况下逃逸的。而且它们是同一类缺陷：agent 把一个代理信号当成了真东西。

0001178 个测试全绿，100% 覆盖率，插件一连真编辑器就崩

根因是一行 export 写错，导致 Loader 丢掉了插件的命名空间。测试全都是手工构造插件，从未走过真实加载路径。

「A test that constructs a plugin by hand cannot validate how the plugin loads.」 / 「Trust the trace, not the theory.」

0002agent 重录了黄金快照，来匹配自己弄坏的行为

一个 disabled: !!js 表达式静默关掉整个文件系统工具栈，横跨 8 个快照场景；刷新把坏掉的记录提交成了期望输出。

「A snapshot refresh is fixture production, not correctness review.」

0003在另一个端口上验证，宣布用户的页面已修好

「源码改了」「构建成功」「HTTP 200」「注入了 boot manifest」「用户现有的页面」被当成了可互换的事实。而那次的回归测试是靠超时通过的。

「The resulting actions were individually plausible but did not share one acceptance target.」 / 「A replacement service cannot prove that an existing page changed.」

0004把结构化失败压成一次子串匹配，测试矩阵照抄了同一个错误表示

原生启动器的丰富协议被降维成前缀匹配，于是普通退出被误判。

「The test matrix mirrored that representation.」 / 「a shared prefix is not a protocol.」

因此 docs/testing.md 的核心指令是一句针对 agent 而写的话——那一节的标题就叫「Verify the world, not the self-report」：

An e2e assertion re-runs the command or re-reads the file externally; a keyword probe on the agent's own output lets a cheating agent pass.

A guard only guards if the regression actually fails it. … introduce the regression, watch red, revert.

07 · 方法的边界

方法在哪里失效：agent 读不到自己输出的地方

如果这套方法有一个失效面，它有名字，叫 packages/client。

这个分组 2026-07-19 才诞生，在最后 3 周半吃下 2,241 次提交、71,896 行，是全仓速度最快的子树。它同时也是所有卫生信号一起退化的地方：

  • 覆盖率闸门的 69 条排除项里有 51 条是 packages/client，配置里直接标注为「GUI debt exemption」，并留了 TODO(gui)。换句话说，那面旗舰级的「每文件 100% 覆盖率」闸门，在全仓最大的一个分组上是关着的。
  • 那次 763 文件的思维链泄漏审计，记录里明说问题「集中在 packages/client」——被删掉的是 (decision 12/16/19/20/21)、(audit C2/S1/S3/S7) 这类只有当时那个会话能看懂的引用，其中只有 decision 21 真的有一份提交进仓库的出处。
  • 复盘 0003 就发生在这里。
可推广的教训

闸门驱动的 agent 开发，在「正确性可以表述成文本」的面上有效，在「验收本质是感知」的面上失效。这也解释了为什么团队要在项目中途临时造出一条 chromium 回放通道和一个专门的 GIF 录制 skill(那份 skill 里写着：Treat one storyboard as one evidence run… never splice frames from separate runs.)，而且债还是欠下了。

残留的「slop」是另一种

真正留下来的问题不是没人读的逻辑，而是仪式性膨胀：219 个 invariant 伴生文件里 184 个是空的(每个都必须写一句为什么空，其中 24 句措辞完全相同)；根 AGENTS.md 卡在 1,900/1,900 词的天花板上，而它自己的规范要求留 5% 余量、目标值是 1,600 词——上限在 40 天里被抬高了 8 次。

这类问题的机制很清楚：当规范要求每个包都产出某种统一制品时，agent 一定会把制品产出来；而当那里没有真话可写，它就会写一句听起来合理的话。闸门能抓住缺失的文件，抓不住内容是仪式的文件。

08 · 人的位置

刻意不交给模型的三件事

一、语气与语义的最终判断。i18n 的 README 里有一句罕见的自我限定，而且中英两版都写着：门禁通过意味着这组文档在当前内容上的一致性得到了确认，不代表确认本身正确可靠。那 187 行术语表是双向绑定的，含 29 条「不要译作」禁令；而遇到表里没有的术语，模型不许当场自创译法——必须保留原文并升级成「待定术语」交给人。

二、一个被锁到只能人工调用的 skill。dsh-translate-docs 是 11 个里唯一的，而且这把锁在两个产品上分别落实(Claude Code 的 disable-model-invocation: true / Codex 的 policy.allow_implicit_invocation: false)，还有一条闸门专门防止两边漂移。锁它的理由不是质量，而是成本控制：

size-based inference is another hidden policy and can unexpectedly activate the expensive workflow. The user, not the agent, chooses when the extended path is worth its cost.

.agents/notes/implemented/process/2026-08-08-lightweight-routine-documentation-translation.md

三、评审技能本身的维护权。这是我在这个仓库里见过最奇特的一条工作流：dsh-code-review 由一个仓库外的私有工具维护，由一位指定的人每天跑一次。它去挖已合并 PR 里的人类评审意见，对照真正落地的补丁验证这条意见是否被采纳，再让两个独立的模型适配器分别起草并交叉评审一份候选 SKILL.md，最后由那个人决定丢弃、攒批还是提升。规则写得很硬：

Do not defer to "the reviewers approved"; the maintainer contract is that the operator makes the final decision.

Do not commit adapter output verbatim. … Days without a skill update are the workflow behaving correctly, not a stall.

docs/cookbook/maintaining-dsh-code-review.md

它的产出率也很说明问题：2026-07-15 那次运行扫了 62 个 PR、426 条人类反馈，产出 0 条新规则。而这条机制自己也记着自己的风险——「单维护者的 bus factor：机制跑在一台机器上，它一中断，skill 维护就完全停摆」。

09 · 可复制性

如果想抄，该抄哪几条

这套东西大致三分之一便宜可移植、三分之一是多人月的资本投入、三分之一只在 DeepSeek 的特定约束下才理性。

值得抄成本为什么
「验证世界，而不是自述」 一页文档 直接瞄准 AI 产出的特有失效模式：看起来合理但从未被外部核验。断言必须重跑命令或重读文件，而不是在 agent 自己的输出里搜关键词。
回归测试必须先见红 一条纪律 引入回归、看它失败、再撤销。两边都通过的守卫什么也没守住。
决策记录 + 强制写被否方案 一个目录 无状态会话之间唯一能继承判断的载体。关键是那句「记录一个决定却不记它打败了什么，就是在邀请重新争论」。
一个 worktree 一个 PR 一条约定 并行 agent 会话共用一个 checkout 是灾难。附带好处：钩子也得按 worktree 装。
把「谁负责」写进记录 零 无法机检的规则要明确写成「评审负责」。这比假装有闸门诚实，也比什么都不写可执行。
陷阱

抄仪式的体量，而不是仪式的用途。219 个 invariant 伴生文件里 184 个什么也不检查——那是 5,538 行什么也不做的样板。评审 skill 里甚至有一条专门防止把自己的规则玩坏：do not demand an invented check merely to eliminate emptiness.

另外三个前提如果不成立，整套方法就不成立：

  • 不需要向后兼容。根 AGENTS.md 里那条豁免是带失效日期的——「在第一个正式版本发布时删掉本节」。能无畏地大规模改名，才是 62 条闸门可执行的前提；一旦有真实消费者，同样的闸门会把树冻住。
  • 不收外部 PR。CONTRIBUTING.md 直接写明。所有被强制的规则因此可以假定作者是同仓库、同团队、agent 驱动的。
  • 推理便宜。docs/testing.md 里那句话只有他们能写：We are DeepSeek — do not ration real-API tests.
10 · 结论

这不是 vibe coding，它几乎是反面

「vibe coding」通常指：提示模型、不细看产出、速度优先、缺乏强验证。这份仓库的证据在每一项上都指向相反方向，而且反驳是写在第 2 天的记录里的——那篇笔记的前提恰恰是「agent 的产出不能托付给散文约定，必须由会失败的命令约束」。之后 64 天里造出来的是：62 条闸门、27.5 万行测试(比源码多)、686 篇决策记录、3.1 万行闸门机器码。

更合适的名字是它的反面：把验收标准写成代码。凡承诺，要么给一条会失败的命令，要么明确写下由评审负责。

但也别把它读成一个成功学故事。同一份证据里有三处诚实的裂缝：那面旗舰覆盖率闸门在全仓最大的分组上是关着的；第 2 天点名的对策(变异测试)在 RC 发布时仍未动工；而 27.5 万行测试只被「跑过没跑过」把关，没被「断言强不强」把关。

如果只带走一句话，我建议是这句——它既是方法的支点，也是它唯一无法被别人直接照抄的部分：

"a lot of work" is not a cost argument when agents do the labor.

11 · 方法

这份报告怎么做的，以及它没能回答什么

13 个并行 agent 分头读一手材料(11 个按流程面：工具证据、指令体系、决策记录、skill、分支拓扑、评审与标签、把关体系、git 取证、复盘、自举、译文与人工判断层；2 个分别扮演质疑「vibe coding」框架和评估可复制性)。此外分支前缀、时段分布、单人速率、双语与笔记同 PR 落地率、以及那三条最有故事性的证据(763 文件的清除提交、50 分钟的 pre-push 实验、泄漏的 worktree 路径)，都由我本人复核过。

最大的证据缺口

git 历史无法区分人写的提交和 agent 写的提交。零条 AI 署名 trailer，所以本文关于人机分工的一切结论，依据是仓库自己的散文(它反复直说)和流程制品，而不是可测量的作者归属。我无法量化 22.7 万行源码里模型写了多少。

其次：没有查询 GitHub。PR 评审串、审批数、返工轮次都在射程之外——对一个关于协作的问题来说，这是最大的一类缺失证据。文中「62 个 PR / 426 条人类反馈」是仓库自己记在一篇 proposed 笔记里的观测，不是独立测量。

另外没有跑测试套件、覆盖率、typecheck、lint 或快照通道，所以本文不声称这棵树整体是绿的。

顺带一处发现：vitest.config.ts 里那句注释引用了 docs/testing.md 的一个说法(「excessive tests are welcome」)，而这句话在 docs/ 里并不存在——一条挂了 64 天的悬空引用。这恰好是本仓库自己那条规则要抓的东西：能否让一个只站在 HEAD、看不到任何会话记录的读者，解析每一个引用、核实每一条断言?
