十一份 Skill，为什么没有组成一条自动开发流水线

这页不把 Skill 当作独立文件逐篇复述，而是把它们放回同一个 Idea 的开发旅程：哪些节点会加载 Skill，Skill 给 agent 什么判断和动作，哪些事情真正由 Hook / CI 强制，以及从 Issue、Worktree 到 PR 之间还留下了哪些空白。

核心判断：DeepSeek Harness 的 Skill 系统是一组按场景加载的工程操作手册，不是 SDLC orchestrator。它在文档、pre-push、review 和 stacked merge 上很强，但没有通用的 Issue、Worktree、Plan、Coding、Test-design 或 PR-creation Skill；人或外部编排器仍然负责把这些局部工作流接成完整开发流程。

Five takeaways

先记住这五件事

最值得学习的不是 Skill 数量，而是它们解决什么失败模式，以及什么事情被刻意留给门禁和人。

  1. 01

    没有 Master Skill

    11 份 Skill 不会自动串成 Issue → Worktree → Plan → Coding → PR；每一份只在自己的触发场景中给 agent 一段局部工作流。

  2. 02

    Skill 是手册，不是门禁

    Skill 告诉 agent 如何判断和操作；真正能自动失败的是 Lefthook、测试、doc-sync、CI 和 GitHub merge requirements。

  3. 03

    覆盖明显后置

    Idea、Issue、Worktree 和通用 Plan 基本空白；最强覆盖集中在写作质量、Push 前证据、PR Review 与 stacked merge。

  4. 04

    五份 Skill 都在治理文字

    文档落位、完整命题、推理残留、双语和网站投影占 5/11，说明 agent 的主要风险之一是写出重复、过期或含混的长期文本。

  5. 05

    按变更类型选择，不是全部加载

    GUI 才录 GIF，stack 才走专用 merge，复杂翻译必须手动调用；上下文成本本身也是需要治理的资源。

01 · System boundary

Skill 是“agent 应该怎么做”，不是“仓库自动替 agent 做”

每个 bundle 的核心是一份带 YAML frontmatter 的 SKILL.md。其中 description 描述何时应加载；正文再给出权威来源、判断标准、命令、禁止项与汇报义务。Agent 读到任务后选择相关 Skill，随后仍然要自己检查仓库、运行命令并解释结果。

Task context→Select SKILL.md→Agent 执行动作→Hook / CI 验证→Human judgment
Skill 擅长

开放式判断与操作顺序

选择最窄测试、判断文档归属、识别推理残留、审查生命周期和并发风险、决定 Agent Note 是否仍有未来价值。

门禁擅长

确定性、可重复的失败条件

类型检查、覆盖率、链接、格式、双语 pairing、生成漂移、快照、平台矩阵和 GitHub merge requirements。

关键边界

Skill 可以要求 agent 做一件事，但 SKILL.md 本身不会在 Git push 时运行，也不会因为 Issue 进入 Ready 就创建 branch。只有被加载、被遵循并最终触发真实命令时，它才产生工程效果。

证据：.agents/skills/ · skill-filesystem README · AGENTS.md · local checks

结构性观察

04 · Requested gap view

它们没有覆盖的地方

沿着完整开发主线看，缺口很明显。下面保留这份调研最直接的版本：

Idea
  ↓ 没有通用 Idea Skill
Issue / Triage
  ↓ 没有创建、分诊或自动派发 Skill
Branch / Worktree
  ↓ 没有自动创建或命名 Skill
Plan / Spec
  ↓ 没有通用 Plan Skill，重大方案改用 proposed Agent Note
Implementation
  ↓ 没有通用 Coding Skill，依赖 AGENTS.md、代码和子系统文档
Testing
  ↓ 没有独立 Test-design Skill
Pre-push
  ↓ dsh-pre-push-checks
PR
  ↓ 没有通用 PR 创建 Skill
Review
  ↓ dsh-code-review
Merge
  ↓ 只有 stacked PR 专用 Skill

所以它们不能自行组成：

Issue→Create worktree→Plan→Code→Test→PR
局部例外不等于通用覆盖

dsh-find-simplifications 可以发现简化 Idea 并写 proposed Agent Note，record-browser-gif 可以补 GUI PR 证据；但它们都没有把普通 Feature Issue 自动转成可执行开发任务。

05 · Core operational trio

三个最接近“开发流程骨架”的 Skill，分别服务作者、Reviewer 和 Merger

dsh-pre-push-checksPR author

把本地 diff 变成可推送证据

  1. 确认 checkout 与 branch
  2. 核实 live PR base / stack parent
  3. 运行 change-scope
  4. 按影响面选最窄测试
  5. Push 后核对远端 SHA 与 CI
dsh-code-reviewPR reviewer

检查机器无法证明的语义

追踪接口两侧、生命周期与并发、真实 Loader / bin / worker 入口、模型看到的 Prompt 与工具 schema、测试是否真的会因回归变红，以及 implemented Note 是否符合 shipped reality。

dsh-merging-stacked-prsMerger

让 GitHub 而不是人维护 stack 状态

重新查询官方 stack，逐层确认非 Draft、Review 和 Checks；使用 gh stack merge 从底向上落地。遇到 blocker 就解决或停止，不退回逐 PR 手工合并。

为什么 pre-push 最核心

它是唯一被根 AGENTS.md 明确要求在 Push 前使用的 Skill，也是本地判断与自动门禁的接缝：Skill 负责选择证据，Lefthook 负责快速确定性检查，CI 负责穷举和平台矩阵。

证据：dsh-pre-push-checks · dsh-code-review · dsh-merging-stacked-prs
06 · Conditional skill clusters

其余八份不是第二条流水线，而是按 diff 特征插入主线的专科手册

文字与文档簇：五份 Skill 处理五种不同失败

doc-standards · 放哪里→prose-standard · 写完整→trim-cot · 去推理残留→translate · 双语→doc-site-sync · 发布投影

这是一张职责图，不是自动调用链。一次普通 JSDoc 修改可能只需要 prose-standard；新增双语网站页面才可能同时触发 placement、prose、translation 和 site sync。dsh-code-review 还会在 Review 时调用 prose-standard 重新做语义检查。

决策治理簇：一份产生简化提案，一份管理 Note 的后半生

dsh-find-simplifications

从证据生成可执行提案

搜索死亡、重复、投机或手写过度的表面；证明候选以后，写 proposed Agent Note、TODO，或合并已经重叠的记录。它是 Idea Skill 的局部特例。

dsh-archive-agent-notes

防止决策记录无限增长

每次新建 Note 都审查同一决策的旧记录；完整替代则合并或归档，部分替代则交叉链接，已无防错价值的 rejected Note 可以成组三文件删除。

GUI 证据：不是截图，而是一条可审计的行为链

record-browser-gif 要求产品用户可见 GUI PR 使用该分支的真实服务器、真实 API key 和真实模型回合录制，并在 PR 旁标注 commit SHA、服务 tree、模式例外和模型是否实际运行。它附带 11 个 Skill 中唯一的可执行脚本资源 scripts/encode_gif.py，但录制与发布仍需要 agent 操作和外部授权。

证据：prose-standard · find-simplifications · archive-agent-notes · record-browser-gif bundle
07 · Discovery and invocation

同一份 SKILL.md 被多个 Agent 入口发现，但没有中央编排器替它们排序

权威目录是 .agents/skills/<name>/SKILL.md。Claude Code 通过受 Git 跟踪的 .claude/skills → ../.agents/skills 软链接读取同一套文件；DeepSeek Harness 自己的 filesystem provider 把 <projectRoot>/.agents/skills 作为 rank 200 的项目技能根。部分 bundle 的 agents/openai.yaml 只提供展示名称、短描述和默认 Prompt，不包含真正执行逻辑。

Catalog time

先只看触发描述

Agent 看到名称与受长度限制的 description，用任务语义判断是否加载正文。

Load time

再读取完整工作流

完整 SKILL.md 带来权威来源、步骤、禁区、命令和最终汇报要求。

Execution time

动作仍由 Agent 发起

Git、pnpm、浏览器、GitHub 和文件编辑不会因为目录里存在 Skill 就自行发生。

唯一明确禁止隐式调用的 Skill

name: dsh-translate-docs
description: Manually run the extended ... workflow
disable-model-invocation: true
user-invocable: true

# agents/openai.yaml
policy:
  allow_implicit_invocation: false

普通双语更新走轻量规则；只有用户明确点名时才加载这套更长的 briefing / delegation / whole-document 工作流。这是一个重要设计信号：Skill 的上下文、时间和模型 token 成本也必须受控。

证据：.claude/skills symlink · project skill roots · translate SKILL.md · translate openai.yaml
08 · Automation boundary

四层共同完成交付：Skill 给判断，Hook 给快检，CI 给穷举，人给方向

Skill

选择测试、判断文档、检查语义、规定安全动作。擅长开放式任务，本身不产生 Git 级阻断。

Hook / scripts

在 commit / push 或显式命令时运行快速、确定性的格式、类型、pairing 与安全检查。

CI / GitHub

执行完整覆盖率、平台矩阵、snapshot、doc-sync 和 merge requirements；失败会阻止合并。

Human

选择 Ready、审重大方案、判断风险与语义、授权 Push / PR / Merge，并承担最终责任。

例子Skill 做什么真正自动执行什么人仍需判断什么
Push根据 diff 选择最窄可信证据，禁止“Push 后指望 CI 不同”pre-commit 快检、pre-push typecheck、CI 全矩阵base 是否正确、哪些回归路径真实受影响
Docs决定事实 owner、文字是否完整、是否含推理残留格式、链接、budget、pairing、生成漂移内容是否真实代表代码与设计理由
Review给出接口、并发、模型视角和测试强度检查表已有测试和 CI 状态是否为真实问题、严重度与合并结论
Stack merge规定官方 stack 查询、范围选择和安全停止条件GitHub 按依赖顺序、检查要求和重定向规则落地是否现在落地整栈或明确的部分边界
不要高估自动化

“模型可以自动选 Skill”不等于“流程已经自动化”。模型仍然需要完整 Issue 上下文、正确 Worktree、仓库权限和决策授权；选错、漏选或只口头宣称完成，都要靠实际门禁和 Review 发现。

09 · Final synthesis

Skills 负责把工程经验交给 Agent；外部编排负责把局部经验接成开发系统

这 11 份 Skill 的设计重点不是“让 Agent 从零自主完成项目管理”，而是把高频、仓库特有、容易出错的判断压缩成可复用文本。它们避免根 AGENTS.md 无限膨胀，也让 Claude Code、Codex 与 dsh 自己可以读取同一套操作知识。

Human / orchestrator→Issue + Worktree context→Agent + selected Skills→Hooks + CI→Human review
真正值得复用

把失败经验写成触发明确的专科 Skill

先由真实事故或反复评审发现模式，再写 Sources of truth、判断标准、禁止捷径与汇报义务；能机械化的部分继续升格为 Gate。

不该误抄

把 Skill 数量当作自动化成熟度

更多 Skill 可能意味着更高上下文成本和更多陈旧点。没有 Issue / Worktree / Plan 编排时，11 份好手册依然不是端到端开发系统。

一句话结论：DeepSeek Harness 的 Skills 是“面向 Agent 的工程经验层”——它们提高执行质量，但没有替代项目管理、任务编排、自动门禁或人的最终判断。

证据口径：固定提交 141eb6f（2026-08-19，dsh-v0.1.0-rc.8；调研时也是 master HEAD）。Skill 数量取 .agents/skills/*/SKILL.md；13,673 为 11 份文件按空白分词合计；6 份 agents/openai.yaml 与唯一 manual-only 配置按该提交树统计。

边界：这里只研究仓库内开发者 Agent 使用的 11 份流程 Skill，不把 packages/skill/ 产品能力、Cordis preset 自带 Skill、测试 fixture 或历史上已删除的产品 Skill 算入。四个簇和“核心 / 条件 / 缺口”是本报告为开发流程建立的分析分类，不是仓库官方 taxonomy。
