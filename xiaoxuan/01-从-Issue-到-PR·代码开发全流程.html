一个 Idea，如何一直走到 PR

不把 Issue、worktree、Agent Note、测试和 CI 分成五个主题。这页只跟踪同一个 Idea：它怎样被记录、分诊、选中、开出独立 worktree，怎样决定要不要先审方案，怎样被 agent 实现与测试，最后怎样成为一个可进入正式评审的 PR。

核心判断：这不是一条“每个 Idea 都先写完整 spec，再自动派发给 agent”的流水线。它是一条分级流程：Issue 在正式评审前必须存在；重大未决方案才先走 proposed Agent Note；代码、测试、文档和决策记录最后在同一 PR 收口。

Five takeaways

先记住这五件事

真正重要的不是 agent 能写多少代码，而是一个想法在什么时候成为承诺、拿到什么上下文，又经过哪些机器和人工门禁。

  1. 01

    Idea 不等于承诺，Ready 才等于开始

    Issue 先进入 Inbox 或 Backlog；只有人确认价值、责任人与验收边界并把它推进 Ready，它才成为真正要实现的开发工作。

  2. 02

    Issue 是开发契约，不是完整 Spec

    固定模板把想法写成可分诊、可验收的任务，但长期设计理由另进 Agent Note；仓库没有统一的“创建 Issue 并自动派发 agent”skill。

  3. 03

    Branch 决定血缘，Worktree 只负责隔离

    独立 PR 通常基于 master，stacked PR 基于直接父 branch；Worktree 是该 branch 的专用工作空间，本身不是 PR，也不会自动完成任务派发。

  4. 04

    方案与测试都按风险规划

    机械修改直接做，已决方案边实现边记录，重大未决方案先审 proposed Agent Note；测试面在计划期命名，但并不强制每项工作采用完整 Spec 或 TDD。

  5. 05

    机器推流程，人守关键门

    Hooks、状态联动、测试与 CI 负责机械一致性；人负责选择 Ready、审重大方案、判断语义与风险。代码、测试、文档和决策证据最终在同一 PR 收口。

01
人决策责任：提出者 / 产品与维护者
起点 · 只是一个可能值得做的想法

Idea 出现时，它还不是给 agent 的任务

主线从一个价值假设开始：也许是新功能，也许是 Bug 现象，也许只是一个还需要研究的问题。仓库的 Idea 模板开头就定义它是“尚未承诺实施、但具有行动可能的想法”。

这一站没有自动 coding。没有 workflow 在 Idea 出现后自动创建 branch，也没有一份仓库 skill 会自动把它派发给 agent。第一个真正动作是：选择正确 Issue Type，把想法写成可分诊的条目。

本步输入

一个价值假设、问题现象或待回答的疑问。

交给下一步

一个已判断类型、可以写入模板的 Issue 草稿。

02
模板 + 机械校验责任：Issue 作者
Idea → Issue · 把“想做”改写成“如何判定完成”

选一份固定模板，把 Idea 写成可验收的 Issue

仓库禁用 blank Issue，入口只有五种原生 Type。这一步不是写完整 spec，而是把需求压缩成正确的问题形状：

Type这一站需要写清
Idea价值假设、需要验证什么、可能的后续工作。
Feature预期结果、验收条件、用户/模型可见变化、测试证据。
Bug复现步骤、实际结果、预期结果、环境与验收条件。
Research核心问题、证据标准、应交付的结论。
Task验收条件、交付物与测试证据。

提交后，policy.mjs 检查标题必须含中文，不得带 Type/Priority/Status/area/Owner 前缀；正文必须有默认收起的 <details>，外露内容不超过 50 单位；Issue 必须进 Project 并拥有合法 Status。多个 Assignee 时还必须显式写 Owner。

没有 Issue 创建 skill

这一站的固定机制是 GitHub 模板和 policy workflow，不是 dsh-create-issue 之类的 skill。当前 11 份 skill 里没有 Issue 创建或 Issue 到 agent 派发流程。

03
人工优先级判断自动化：状态合法性与后续 PR 联动
Issue → Ready · 这里才决定是否真的开发

Issue 先进 Inbox，再由人把它推到 Backlog 或 Ready

这是 Idea 到代码之间最重要的人工判断点。Project 的状态集合是 Inbox → Backlog → Ready → In progress → In review → Done / No action。可见 workflow 会维护状态与 Issue/PR 事件的一致性，但不会自动判断一个 Idea 是否值得进 Ready。

Inbox→Backlog→Ready→In progress→In review→Done / No action

只有我们正在跟踪的这个 Idea 被选中实现时，它才会带着所有者、可选的 P0–P3 Priority 和验收边界进入 Ready。没被选中的 Idea 可以留在 Backlog，或以 Not planned 关闭并对应 No action。

04
创建自动化低建好后：worktree-local hooks 自动接线
Ready → branch / worktree · 把任务变成独立代码空间

对独立改动，从 master 开；对 stacked PR，从直接父 branch 开

当前默认分支是 master。如果这个 Ready Issue 会形成一个独立 PR，它的基线通常是已核实的最新 master。如果它是一条依赖 stack 的 B 层，则 B 基于 A branch，不能假装 B 可以单独相对 master 开发。

独立：master → feature branch → dedicated worktree
Stack：master ← PR-A / worktree-A ← PR-B / worktree-B ← PR-C / worktree-C

仓库没有“输入 Issue 号，自动创建 branch 和 worktree”的命令，branch 命名也不统一；历史中同时存在 worktree/、codex/、agent/、feat/、fix/ 等家族。自动化从创建之后才开始：pnpm install 的 postinstall 会为当前 worktree 安装独立 Lefthook 和翻译 pairing merge driver。

概念边界

Worktree 是本地 checkout 的隔离容器。最后提 PR 的是它所 checkout 的 branch，不是 worktree 目录本身。Stack 中强约定是“每个 PR branch 一个 worktree”。

方案判断由 review 负责自动化：Agent Note 格式与配对门禁
Worktree → implementation-ready · 不是所有任务都先写 spec

在真正实现前，先判断这个变更属于哪条设计路径

这里不是一刀切的 spec-driven development，而是按决策风险分三路：

路径 A · 机械 / 纯局部

可跳过 Agent Note

不改行为、架构、跨文件约定、流程或理由的改动免除。

路径 B · 决策已明确

直接实现 + implemented/

非平凡改动在同 PR 写或更新 Agent Note，方案与代码一起评审。

路径 C · 重大且未决

先评审 proposed/

实现前先审 Problem、Proposal、Alternatives considered、Acceptance criteria 和 Risks。

这就是“有没有 Plan Review”的准确答案：重大未决方案有实现前评审，载体是 proposed Agent Note；但没有所有任务统一经过的 Plan approved 状态，也不要求所有工作先交一个独立 Plan PR。仓库产品里的 Plan mode 是另一个同名功能，与开发审批无关。

有没有专门的 Plan / Spec Skill？

直接答案

没有通用的 write-plan 或 create-spec skill；有统一的 Spec 载体和格式。仓库现有 11 个开发 skill 覆盖文档、评审、pre-push、stacked PR、Agent Note 治理和 GUI 证据，但没有一个负责把所有任务自动写成 Plan。重大未决方案使用 proposed Agent Note，它才是这里最接近正式 Spec 的东西。

问题仓库里的答案
专门的 Plan / Spec skill没有通用版本；只有面向特定工作的相邻 skill，例如简化提案或 Agent Note 归档。
固定格式有。verify-agent-note-format 会机械检查 lifecycle、状态和规定章节。
每项任务都先写不是。只有重大且尚未决定的未来工作先进入 proposed/。
单独的 Plan PR没有仓库级统一要求；真正要求的是重大方案在实现前先被 review。

Proposed Agent Note 的固定骨架

# Agent Note: <title>

Status: proposed

## Problem
## Proposal
…与方案有关的技术章节…
## Alternatives considered
## Acceptance criteria
## Risks

Proposal 可以包含实现步骤、迁移方式和开放问题；测试需要在这一阶段命名 unit、e2e 与 snapshot 覆盖，但不要求预先枚举每一个 test case，也不强制 TDD。

实现之前

描述准备做什么

Problem → Proposal → Alternatives → Acceptance criteria → Risks，以未来时态接受方案评审。

实现之后

改写成已经发生的事实

Proposal → Decision，验收与风险折入 Consequences / Testing / Verification；implemented Note 不再保留过期的 Plan 清单。

不要混淆

packages/plan/ 是 DeepSeek Harness 产品自身的“Plan mode as logged state”，不是维护者开发这个仓库时使用的 Plan 审批 skill，也不代表每个 Issue 都自动进入 spec-driven 流程。

测试在这一步就开始被规划

新 capability seam、生命周期路径或 transcript 表面，必须在 plan time 命名 unit、e2e 与 snapshot 覆盖，并在实现前确认测试 harness 表达得了。这是“提前规划测试面”，但不是“每个 test case 必须先写红”的强制 TDD。

Ready Issue + 独立 worktree + 现有设计记录。

交给下一步

一个已选定的方案路径、验收条件和测试证据地图。

启动 agent 的编排不在公开仓库仓库自动提供：指令与可执行规则
Design → implementation · 现在才进入写代码阶段

Agent 进入 worktree，但 Issue 不会被 Git 自动复制进来

Git worktree 会带来 branch 中已跟踪的上下文：根目录与子树 AGENTS.md、开发与测试文档、已提交的 proposed/implemented Agent Notes，以及 .agents/skills/ 中的流程指导。这些是实现者的长期规则。

但 GitHub Issue 正文、Project Priority、Issue 评论和未来 PR review thread 不是 Git 文件，不会随 worktree checkout。因此必须由人或外部编排器把这个 Ready Issue 交给 agent。没有发现 Issue → Markdown spec → agent prompt 的仓库内自动同步器。

Implementation → evidence · 让每个验收条件有一条会红的证据

实现不算完成；现在按可见面把测试证据补齐

这一站不是无条件跑全仓库。实现者先根据第 05 步的测试地图，为每个改变的行为选择会因该回归而失败的最窄证据：

Unit边界、错误路径、事件顺序、并发竞争与回归约定。
CoverageCI 对 packages/*/*/src 要求每文件 100%；但 coverage 只证明行被执行，不是产品验收。
Real composition产品可见插件必须通过 Loader 和真实 app/process 启动；手工 ctx.plugin(...) 不够。
Snapshot模型、协议或人类可见变化，必须在同 PR 更新真实可运行示例所属的 keyless snapshot。
Real API e2e需要时用真实 DeepSeek/provider 验证文件写入、多轮、工具调用与取消。

e2e 断言会重新读文件、重新执行命令或检查持久状态，不能只搜索 agent 输出里是否说了“成功”。强回归保护还应在未修复代码上被证明确实会失败。

08
本地 hook 自动证据范围：人 / agent 先核实
Evidence → pushed branch · 本地收口

先核实 diff 的真实 base，再 commit，最后让 pre-push 检查类型

dsh-pre-push-checks 要求先确认当前 checkout 和 branch，核实活跃 PR base 或 stack parent，然后运行 change-scope --base <verified-base>。这个命令故意不猜 base，因为错的 merge base 会让 agent 忽略真正差异。

随后执行第 07 步挑出的最窄检查：行为改动跑 owning tests，文档跑 doc-sync，可见输出跑 snapshot，发布路径跑 build/hygiene/built smoke，真 provider 行为在有密钥时跑 e2e。仓库明确反对反射性跑全套；穷举是后面 CI 的工作。

09
PR policy 自动校验责任：PR 作者整理意图与证据
Pushed branch → PR · 把实现 diff 与最初 Issue 重新接上

现在从 worktree 对应 branch 建 PR，但 PR 不是上传 worktree

提交对象是远程 branch。PR 模板故意很短：关联 Issue，再在折叠区写“变更”和“验证”。如果这个 PR 解决了我们一直跟踪的 Issue，写 Fixes #NN；只是相关上下文则写 Related to #NN。

Issue 不一定在写第一行代码前就存在

Draft PR 和本地实验可以更早开始。但当一个人类作者的非 Draft PR 已请求或收到人工 review 时，policy 必须看到至少一个同仓库 Issue。所以它是 review-time Issue mandatory，而不是可执行规则上的 code-before-everything Issue mandatory。

进入正式人工评审前，PR 必须收齐这些元数据

  • 正文至少引用一个同仓库 Issue。
  • 恰好一个允许的 kind/*，至少一个 area/*，至多一个 P0–P3。
  • 解决型 PR 的 Priority 与 Issue 同步；解决多个时取最高优先级。
  • 非平凡变更包含 Agent Note；用户/模型可见变化包含 snapshot；公开行为同步 README/JSDoc 和双语对侧。
  • PR “验证”只写真正跑过的本地命令，未完成的 CI 必须仍然报告为 pending。

10
CI 穷举人工 review 语义
PR → reviewable PR · 主线在这里完成

PR 创建后，CI 与 review 反复验证它是否真正代表最初 Idea

CI 不是等代码“全部开发完”后只跑一次。PR 后每次 push 都会重新执行对应 workflow：完整 coverage、snapshots、docs、build、平台矩阵、包安装与单独的 real-API e2e。本地检查负责快反馈，CI 负责穷举。

人工 review 不重复绿灯已经证明的机械事实，而是核对 Issue 的意图、Agent Note 的决策、生命周期和并发正确性、真实入口、测试是否真能抓住回归、snapshot 差异、文档与双语语义。

PR opened / synchronized→Issue: In progress→review requested: In review→changes requested: In progress↺

如果 review 要求修改，实现者回到原 worktree，修复最先引入问题的那一层 PR，重跑被修改影响的本地证据，push 新 commit，再让 CI 和 review 重新评估当前 HEAD。Stack 中修复从引入层向上传播，每层都必须独立通过。

到这里，一条主线才完整：Idea 没有直接变成 agent prompt；它先变成可验收 Issue，经人工分诊成为 Ready，再开独立 worktree，按决策风险选择是否先审 proposed Agent Note，由人或 agent 同步产出代码、测试、文档与决策记录，通过本地证据和 hooks 后 push，最后用 PR 把实现重新绑回最初 Issue，交给 CI 与人工 review。

本报告在 PR 收口处停止。后面的合并、master 后置演练和发布是另一条流程，不再打断“Idea 如何到 PR”这条主线。

本步输入

元数据齐全的 PR 和它的当前 head commit。

主线终点

一个关联 Issue、证据齐全、通过 CI，并且人工意见已收敛的 reviewable PR。
