DeepSeek Harness Documentation governance Snapshot 141eb6f

一份文档，如何陪着代码从 Idea 走到归档

这页只沿一条线追踪：同一个开发想法如何先成为 Issue，如何决定文档应该放在哪里，何时产生 proposed / implemented Agent Note，怎样与 README、JSDoc、双语对侧和生成型参考一起进入 PR，最后怎样持续维护、被替代或冻结归档。

核心判断：DeepSeek Harness 不是在开发结束时“补文档”，也不是要求每个任务先写一份完整 Spec。它采用的是决策驱动、代码同仓、生命周期可验证的文档体系：Issue 管任务，Agent Note 管理由与取舍，README / JSDoc 管当前契约，Snapshot 管可见行为，Postmortem 管失败历史。

Five takeaways

先记住这五件事

真正值得复用的不是文档数量，而是信息如何归属、怎样随代码交付，以及人和自动化分别负责什么。

  1. 01

    文档就是交付物

    代码、测试与相关文档在同一个 Worktree、同一个分支和同一个 PR 中完成；文档没有跟上，功能就还没有真正完成。

  2. 02

    一个事实只有一个 Owner

    Issue 管本次任务，Agent Note 管设计理由，README / JSDoc 管当前契约；其他位置链接过去，不复制出多个真相。

  3. 03

    风险决定流程重量

    机械修改直接实现，方向明确的变更补 implemented 记录，跨模块或高风险决策才先写 proposed 并接受审查。

  4. 04

    机器验一致，人验真相

    doc-sync 负责格式、链接、双语、生成漂移等机械约束；人负责判断理由是否成立、内容是否真实代表代码。

  5. 05

    仓库必须成为 Agent 的显式记忆

    Worktree 只会带入已版本化的规则与文档，不会带入私聊和隐含需求；重要上下文必须写下来，并持续维护、替代或归档。

01
价值与验收由人确认自动化：模板与 Issue policy
Idea → work item · 第一份文档不是完整设计稿

先把想法压缩成一个可分诊、可验收的 Issue

仓库提供 Idea、Feature、Bug、Research、Task 五种模板。它们都要求标题是中文行动或结果句，外露正文只保留一句话，详细内容放进默认收起的 <details>。Feature 和 Task 要写验收与测试证据，Bug 要写复现、实际结果与预期结果，Research 要先定义证据标准。

因此 Issue 的职责是建立任务和验收边界，不是承载长期架构理由。它可以随着讨论变化，也不会被 Git worktree 自动带入；真正需要随代码长期保存的决策，后面进入 Agent Note 或当前状态文档。

Issue 拥有

What

问题、预期结果、验收条件、证据标准和交付物。

Issue 不独占

Why

长期设计理由与被放弃的替代方案交给 Agent Note。

进入下一步

Ready context

被选中实现、责任清楚，并具备可解释的完成边界。

本步输入

一个想法、故障、研究问题或明确任务。

交给下一步

一份短而结构化、可以被分诊和验收的 Issue。

证据：.github/ISSUE_TEMPLATE/ · .github/issue-management/policy.mjs
02
归属判断不可机械化原则：one home per fact
Ready Issue → document map · 先决定放哪里，再开始写

同一个事实只允许有一个正式归属，其他地方链接过去

docs/AGENTS.md 把文档体系定义成多个有边界的层。写作者先判断文档的主题、读者和用途，再选择 tutorial 或 reference，并把更低层细节移到真正拥有它的地方。 durable prose 只描述当前事实；变更历史留在 commit / PR，决策理由留在 Agent Note，事故时间线留在 Postmortem。

文档层它拥有的事实不应该放进去
根 / 子树 AGENTS.md每次工作都需要的长期指令；子树只写本区域特有规则教程、故事、重复的 repo-wide 规则
architecture / subsystems整体组合地图；类型定义与 subsystem 语义每个 package 的实现细节、设计历史
Package README / JSDoc配置、语义、失败、限制、扩展点和调用方契约生成目录的重复清单、其他包的责任
Agent Notes决策理由、替代方案、后果和必需验证用户教程、已交付后的计划清单
Cookbook / user docs可执行步骤与公开产品使用方式内部决策史、维护者专用流程
Skills / Postmortems可复用工作流；事故证据、因果链和防复发措施产品运行时契约；普通功能变更史
关键治理规则

“一个事实一个家”并不禁止关键契约在调用点出现，但扩展解释只能有一个 owner。其他文档以可机械检查的相对链接引用它，避免复制后分别老化。

本步输入

Ready Issue、受影响的代码面和已有文档。

交给下一步

一张文档责任图：哪些事实更新原 owner，哪些需要新决策记录。

证据：docs/AGENTS.md · dsh-doc-standards/SKILL.md
03
重大未决方案先 review自动化：分类、格式、状态与配对
Document map → decision route · 不是所有任务都先写 Spec

按决策风险选择机械、implemented 或 proposed 三条路

机械 / 局部

Agent Note 免除

不改变行为、契约、结构、流程或可被重新讨论的理由。

决策已经明确

直接写 implemented

代码与决策记录在同一个 PR 里一起接受评审。

重大且尚未决定

先写 proposed

实现前评审 Problem、Proposal、Alternatives、Acceptance criteria 和 Risks。

proposed→implemented→archived／rejected

每个非平凡变更必须在同一 PR 新增或更新至少一份 Agent Note，但“这个 diff 是否非平凡”“旧 Note 是否已经拥有该决策”需要语义判断。格式检查只能验证现有 Note 是否放在合法 lifecycle / class 目录、是否包含规定章节，不能自动判断缺失的设计理由。

Proposed 不是最终文档

实现完成后不能只改一行状态。Proposal 要重写成当前时态的 Decision，验收与风险要折叠进实际 Consequences、Testing 或 Verification；已经 shipped 的 Note 不再保留迁移计划和未来式清单。

Plan / Spec 的开发流程归属

这里不重复 Plan skill、固定 Spec 骨架和实现前 review 的完整说明；它们由第一份报告第 05 步：有没有专门的 Plan / Spec Skill？统一解释。

本步输入

文档责任图、已有决策记录和方案不确定性。

交给下一步

可直接实现的决定，或一份已经审过的 proposed Agent Note。

证据：.agents/notes/README.md · implemented/AGENTS.md
04
Git 自动携带版本化文档Issue 元数据需另行注入
Decision → worktree context · 文档与源码使用同一版本

Branch checkout 的不是裸代码，而是一整套版本化开发上下文

他们没有独立文档仓库。创建 worktree 后，当前 branch 中的根与子树 AGENTS.md、现有 Agent Notes、架构与测试文档、Package README、Skills、生成器和站点 manifest 会与代码一起出现。Agent 读到的规则和它要修改的代码天然处于同一个 commit。

Git 已带入

长期版本化上下文

  • 根与子树 AGENTS.md
  • active Agent Notes 与文档树
  • Package README / JSDoc owner
  • 文档 Skills、生成器与门禁源码
Git 不会带入

远程任务上下文

  • Issue 正文、评论和 Project 字段
  • PR review thread
  • 私有讨论和 orchestrator prompt
  • 尚未提交的临时方案

这保证“文档随代码分支演进”，但不保证 Agent 自动获得完整任务。外部编排器或人仍要把 Ready Issue 注入当前 worktree；一旦开始实现，长期规则和交付文档都在同一 diff 中维护。

本步输入

已确认的设计路径、目标 branch 和远程 Issue 上下文。

交给下一步

代码、规则、现有事实与决策记录版本一致的实现环境。

证据：AGENTS.md · .agents/skills/ · docs/
05
Agent 可执行大部分更新文档完整性需语义判断
Worktree → complete diff · 文档不是尾声，而是交付物

实现代码时，同时更新契约、决策、公开说明和可执行证据

根规则明确要求 docs accompany every code change。实现者先改真正拥有事实的源，再让派生文档跟随：Package README 写配置、语义、失败、限制与扩展点；JSDoc 写调用方可见的返回、异常、所有权、时序和副作用；核心类型变更同步 subsystem 页面；用户或模型可见行为同步公开文档与真实 runnable-example snapshot。

代码变化同一 diff 中对应的文档责任
Package 配置或默认值Package README、相关 JSDoc；生成型 config catalog 后续重建
公共 API / 失败行为公开 JSDoc、owner README；必要时 type-equiv / subsystem
架构或跨包契约architecture / subsystem owner + Agent Note 的理由与后果
用户或模型可见输出用户文档、稳定可见字符串，以及真实组合的 keyless snapshot
操作流程Cookbook；长期 agent 执行规则才进入 AGENTS.md 或 Skill
proposed 方案完成移动到 implemented，重写为实际 shipped 的当前事实

文档不保存 Agent 的推理过程、review 对话或代码已经明显表达的控制流；它保存后续维护者仍需要依赖的契约、理由、负面保证、例外与后果。可见文本被视为行为，Snapshot 则成为文档与测试之间的可执行连接。

本步输入

版本一致的 worktree、实现决定和文档责任图。

交给下一步

源码、测试、README/JSDoc、Agent Note 与可见行为证据完整的 diff。

证据：AGENTS.md · dsh-prose-standard/SKILL.md · docs/testing.md
06
完整性、hash 与结构自动检查翻译语义必须 review
Changed prose → atomic pair · 双语不是合并后的翻译任务

每份纳入范围的文档以三文件原子单元进入同一个 PR

英文和简体中文拥有同等权威；一次更新可以从任意一侧开始。它们不放进 locale 目录，也不存进独立翻译仓库，而是与 consistency sidecar 同目录并排：

foo.md

英文对侧；普通 authored 文档包含中文切换链接。

foo.zh.md

中文对侧；标题层级、列表、表格、链接和代码块与另一侧镜像。

foo.i18n.yaml

保存两侧最后一次确认一致时的完整 Git blob hash。

任意一侧变化后，只对 counterpart 做覆盖该 diff 的最小更新，保留未触碰的已审文案，然后运行 verify-translation-pairing --write <pair> 重新记录两个 hash。配对 merge driver 只能在双方文本合并与结构验证都安全时自动组合 sidecar，否则保留普通冲突。

绿色门禁的边界

自动化可以证明“三个文件存在、当前内容等于已确认 hash、结构彼此对应”，但无法证明翻译准确、自然或术语正确。重新记录一份糟糕翻译同样会绿，因此语义一致性属于 reviewer。

本步输入

已经完成语义更新的英文或中文文档。

交给下一步

两种语言同步、结构一致且 sidecar 已重新确认的完整 triplet。

证据：docs/i18n/README.md · dsh-translate-docs/SKILL.md
07
生成与投影可重建公开范围由 manifest 决定
Canonical sources → derivatives · 派生物不能反过来成为 owner

先更新源码与 owner 文档，再重建目录、图表和公开网站

Tool、config、persistence、Cordis API、module graph 等参考页是从源码或 JSDoc 生成的英文 source。它们不能手改；如果页面过时，要修改真正的代码、注释或生成器，再让 freshness gate 验证重新生成后的结果。生成页有已审中文 counterpart 时，中文仍按普通 pairing 流程更新。

canonical Markdown→website/docs.ts→website/.generated→VitePress build

文档网站同样没有第二套可编辑源。website/docs.ts 是显式公开 allowlist：固定快照中，它只映射 15 个 canonical Markdown source；中文投影到根路由，英文投影到 /en/。website/.generated/ 是可丢弃构建树，不能手改或提交。内部 Agent Notes、Postmortems、测试指南和维护流程不会因为位于 docs/ 就自动发布。

Source of truth

仓库 owner

源码、JSDoc、Package README、canonical Markdown、生成器和网站 manifest。

Derivative

可重建产物

生成型 catalog、graph、网站 projection、snapshot 与 fixture；修改 owner 后再更新。

本步输入

已完成双语同步的 owner 文档，以及发生变化的源代码 / 元数据。

交给下一步

新鲜的生成参考、合法的公开映射和可构建的网站投影。

证据：generated reference taxonomy · website/docs.ts · dsh-doc-site-sync/SKILL.md

28 项 doc-sync 门禁本地相关检查 + PR CI 穷举
Complete diff → mechanically consistent · 机器验证可形式化的部分

pnpm run doc-sync 在该快照中展开为 28 个 leaf gates。它不只是 Markdown lint，而是同时验证文档与代码、生成源、双语、Agent Note 生命周期和网站构建之间的关系：

本地 hook 故意保持很窄：pre-commit 处理 staged pairing record、lint、whitespace 等，pre-push 只跑 typecheck。文档变化由实现者按 dsh-pre-push-checks 选择 doc-sync；CI 的 static lane 再执行完整集合。这避免每次 commit 都重跑大型站点与文档图，同时保证 PR 最终无法绕过。

机器能证明什么

链接存在、代码块能编译、复制的类型没漂移、生成物新鲜、结构合法、pair hash 匹配、站点能构建。机器不能证明内容放对了地方、理由真实、句子准确或翻译表达了相同含义。

本步输入

代码、测试、文档、双语 triplet 和所有派生物构成的完整 branch diff。

交给下一步

所有可形式化约束都已通过、可以交给语义评审的 PR 内容。

证据：scripts/run-gates.ts · lefthook.yml · .github/workflows/ci.yml
09
CI 验证机械一致性Reviewer 验证语义与归属
Green gates → trustworthy prose · 绿灯只是语义评审的起点

PR review 不重做机器检查，而是确认文档确实代表代码与最初意图

PR 模板只要求关联 Issue，并在折叠区写“变更”和“验证”；真正的文档验收来自 code-review 规则。Reviewer 要检查新 Markdown、JSDoc、comment、prompt、diagnostic 和 visible string 的准确性、位置与编辑质量，确认 config、default、error、wire field、event 和公开行为已经同步到 owner README / JSDoc。

自动检查已经覆盖

Structure

  • 链接、锚点、格式和预算
  • 生成目录与源的一致性
  • 双语 hash 与结构
  • 站点投影和构建
人工必须补上

Meaning

  • 事实是否属于这一层
  • 理由与替代方案是否真实
  • 文档是否完整匹配 shipped 行为
  • 中英文含义与术语是否一致

如果 review 发现文档与代码不符，修复回到原 worktree：先改 owner，再更新 counterpart 和 derivative，重新运行受影响的 doc-sync gates，push 后让 CI 对新的 HEAD 重新评估。一个 re-recorded pairing sidecar 只代表作者声称确认过，不能替代 reviewer 的逐条语义比较。

10
未来决策价值由人判断自动化：归档 triplet 与 append-only hash seal
Merged decision → maintained memory · 合并不是文档生命周期终点

保持当前事实；被替代时保留理由；价值耗尽后才冻结归档

合并后的普通文档和 active implemented Agent Note 都继续描述当前状态：代码路径、symbol、default 或机制变化时，在同一次改动中更新事实，不追加“以前如何、现在如何”的变更史。若原决定被反转，应创建新的 Note 并交叉链接；只有完整替代且新 owner 保存了所有独特理由、替代、后果和覆盖缺口时，旧 active Note 才能整合删除。

implemented · keep current→superseded · cross-link→archived · frozen／rejected · keep or delete

归档不是按年龄、字数或配额执行，而是看未来决策价值。仍包含 ownership boundary、negative guarantee、durable / wire semantics、安全规则或重新引入条件的 Note 保持 active；一次性实现细节且未来不再指导决策的 complete implemented Note 才移动到 archived/{class}/。

Archive

冻结设计历史

移动完整英文、中文、sidecar triplet，只添加同一天的 Archived 行并重录 hash。seal 后永不编辑、翻译、移动或删除，也不再是当前 authority。

Postmortem

记录逃逸事故

当 bug 微妙、系统性且重发现代价高时，记录事故时间线、根因、为什么所有防线都漏掉，以及新增的永久 guardrails。

整条文档主线到这里才完整：Issue 保存一次开发任务的目标，Agent Note 保存可复用的决策记忆，README / JSDoc / docs 保存当前契约，生成参考与网站从这些 owner 投影，doc-sync 保证机械一致，review 保证语义正确；合并后仍有价值的知识持续维护，失去当前 authority 的记录才进入不可变历史。

本步输入

已经合并、仍会随代码继续演进的文档与设计记录。

主线终点

一个当前事实清楚、历史理由可追溯、旧记录不会伪装成现状的知识库。
