01 · 核心判断

vibe coding 在这里的含义：把「团队默契」全部机械化

仓库建立第二天回填的第一批决策记录里，「质量闸门」一篇就把前提说死了：「这个代码库主要由 coding agent 开发。agent 遵守强制闸门的可靠程度，远高于遵守散文约定。」此后 65 天的一切流程设计都是这句话的推论——凡是能机械检查的承诺，都变成一条会以非零退出的命令。

所以这套方法和通常语境里的「vibe coding」相反：它不是放松纪律，而是把纪律从人脑搬进仓库。团队默契被拆成三种可执行物——给 agent 看的规范（15 份 AGENTS.md 与 11 个 skill）、agent 每次改动都会撞上的闸门（62 道）、agent 会话之间传递的记忆（683 篇 Agent Note）。人退到三个位置：定方向、review、按下 merge。

证据链是三层的。第一层是 git 里的直接痕迹：56% 的 PR 来自 codex/、worktree/、claude/ 这类由工具命名的分支；1,886 次提交信息里出现 Codex；有 95 次非合并提交的信息里提到「codex review」，其中 36 次的标题就是「address codex review round N」之类。第二层是仓库自己怎么说：AGENTS.md 曾经写过一句「在 agentic-coding 时代，代码大多由机器写、由机器读，严格性的成本收益已经反转」。第三层是一份两天后就被从工作树里删掉、但仍能从提交 0681ac47de 读出的 missions/ 目录——里面是一位工程师用 Claude Code 指挥九个常驻 teammate agent、五天造出 Web GUI 的工作台账（第 10 节）。

这卷报告要回答三个问题：谁在写（第 2 节）、一次改动怎么从 Issue 走到发布（第 3 节）、以及为什么这套流程长成这样——每一条规则背后几乎都对应一种 agent 特有的失败模式（第 11、12 节）。

谁在写代码：三个人、二十多位同事、以及无名的 agent 会话

一个刻意的空白

整部历史里没有一条「Co-Authored-By: Claude」或「Generated with Claude Code」尾注——不是没用，而是不写。被删除的 missions/conventions.md 第 4 条写着：「commit message 不携带 Co-Authored-By 等 co-auth 尾注」。所以 git 作者永远是人：每个 codex/、worktree/、claude/ 分支上的第一个提交都带 +0800 时区、绝大多数（539 / 552）作者即提交者、用个人或公司邮箱。分支家族与工具的对应关系因此是推断：codex/ 是 Codex（CLI/App）的默认命名；worktree/ 与 .claude/worktrees/ 下的临时 checkout 有直接证据（一次误提交的 .claude/launch.json、一次误提交的 gitlink），并且有 worktree/charming-swartz-83bf33 这种 Docker 式随机名，符合 Claude Code EnterWorktree 的行为。

合并拓扑：不 squash，不 rebase，向前合并

5,610 次合并提交里只有 984 次是 PR 合并，其余是 1,848 次「Merge remote-tracking branch 'origin/master' into …」、587 次「Merge branch 'master' into …」（其中 532 次是 GitHub 网页上的 Update branch 按钮）、以及其余约 2,200 次——其中约 1,800 次是分支之间的传播（一个 codex/simp-ui-identity-residue 分支五天里被合进它的子分支 111 次）。全部 984 个 PR 都是真正的 merge commit，0 次 squash。这是 6 月 16 日就写进 AGENTS.md 的决定：「每个 PR 的提交历史是刻意保留的——review 修复提交、回归测试提交……都是记录的一部分，squash 会把它压平」；6 月 21 日又补上已推送的分支禁止改写，因为那会「打断 stacked-merge 图并抹掉 review 修复历史」。7 月 28 日起允许改写未合并 PR 的已推送历史，8 月 2 日定为带 lease 的 rebase，raw --force 始终禁止。

结果是一个「合并优先」的图：主干 first-parent 上 943 次合并（942 次 PR 合并 + 创始人 6 月 18 日直推的一次合并）+ 29 次直接提交（全部是创始人 6 月中旬之前的），此后没有人直接推 master。

03 · 从 Issue 到发布

一次变更的生命周期：九站，人只把守四站

把散落在 .github/、lefthook.yml、skill、Agent Note 里的规则串起来，一次典型改动走的路径如下。人明确把守的是四处：Issue 拍板、review、merge、release；其余由 agent 完成，但每一步都有对应的机械检查。

三个细节决定了这条流水线的手感。其一，Issue 与 PR 的入口是中文的。五个 Issue 模板、PR 模板、policy.mjs 的报错信息全是中文；PR 模板只有三行：「关联 Issue」「变更」「验证」。规则却是英文且机械的：非草稿、有人 review 的 PR 必须引用至少一个同仓库 Issue，恰好一个 kind/*、至少一个 area/*，若写了 Fixes 则优先级要与最高的 Issue 对齐。其二，review 是分层的。先由 agent 做多轮「收敛评审」——git 里有 129 次「review round」提交、95 次「codex review」，7 月 3 日起又有一个内部的 ds-review-bot 出现在 99 次提交信息里并在 7 月下旬取代 Codex 成为最常被点名的评审者——再由人审语义、文档与「这个改动算不算非平凡」；仓库明确拒绝为「非平凡」写自动分类器，「Review enforces the semantic boundary」。其三，合并即发布链的起点。每个 PR 都会干跑一次 pack，真正发布靠人手动 bump 版本、走 workflow_dispatch，由 npm registry 按版本号与 integrity 决定发布、跳过还是失败——8 月 11–13 日 imccyu 连续切了 9 次版本，从 0.0.1-rc.1 到 0.1.0-rc.5。

专门写给 agent 的句子

根手册里有一批规则，只有假设读者是 agent 才说得通：

  • 「Host sandbox failures」（7 月 15 日加入）：当 gh/pnpm/构建因为「agent 沙箱阻止了凭据、网络、IPC、文件监听或嵌套 sandbox-exec」而失败时，「以最窄的宿主提权原样重试」，并且「要求沙箱证据；永远不要绕过真正的测试失败或被测的产品沙箱」。
  • 「report only commands run」——只汇报真正跑过的命令；配套的 skill 说得更直白：「不要 push 然后指望 CI 结果会不一样」。
  • 「Comments and docs state complete contracts and context, not reasoning transcripts」「Do not use metaphors」「Do not comment on facts obvious from code」——后两条分别于 8 月 9 日（PR #2103，codex/concrete-technical-prose 分支）和 8 月 12 日（PR #2335，codex/comment-obvious-code 分支）由同一位作者加入。
  • 「Trust TypeScript at typed same-process boundaries」：不要为类型系统已经保证的值添加运行时校验、回退或恶意输入测试——这是 agent 最常见的过度防御。
  • 「Pre-release stance」：整节以「Remove this section at the first tagged release」开头，告诉未来的 agent 在何时删掉自己；早期版本还有一句「Churn now is cheap; a wrong foundation set in stone is not.」

写给 agent 的测试纪律

  • 先证明它会红。7 月 3 日版手册把「每条回归测试必须在未修复的代码上被证明失败」列为「头条纪律，不是脚注」：注掉修复、看测试变红、再恢复；「一个正反都过的守卫什么也守不住——而一片绿的 100% 覆盖套件恰恰会把这一点藏起来」。
  • Test the real entry path。来自事故 0001：一处多余的 export default 让 Loader 丢掉了 inject，「178 个绿色单测和 100% 行覆盖」全没抓到，因为测试是手工挂载插件的。
  • Fixture 坏了修 fixture，不修归一化器。可追溯到一次删除「为 GNU sed -i 打补丁的归一化 hack」的提交。
  • 等事件，不 sleep。「一次因超时导致的属性测试抖动是一个发现，不是要重试掉的东西」；唯一被批准的重试只在真 API 配置里。
  • 每个非平凡的模型/用户可见改动都要在同一 PR 里通过一个真实可运行的示例新增或更新 keyless 快照——包测试、纯 e2e 断言、纯 mock fixture 都不算数。

快照机制有一个漂亮的自反性：它复用产品自己的持久化格式当 fixture，于是「模型看到的 ⟺ 日志里有的」这条架构不变式，同时也是测试基础设施成立的前提。1,872 次提交触碰过快照 fixture 目录——每次模型可见输出的改动都要「重录」，这就是 agent 时代的 review 对象。

机制上，一对文档是三个兄弟文件，.i18n.yaml 记录两侧的 git blob 哈希——上次被确认一致时的内容。任何一侧一改，闸门就红，直到对侧被更新并用 verify-translation-pairing --write <pair> 重新记录；那份 yaml diff 就是「确认一致的可评审动作」，裸跑 --write 会被拒绝，因为「记录你没审过的 pair 等于给未确认的内容盖章」。闸门还比对结构签名（标题深度、字节相同的代码块、表格维度、列表种类与数量、链接目标），但它明确承认自己不懂语义：「绿灯只说明这一对在这个确切内容上被确认过一致，不说明那次确认是可靠的……那是 reviewer 的那一半契约。」配套的还有一个 .i18n.yaml 的 git merge driver、pre-commit 里对暂存 sidecar 的 --cached 校验，以及一个能把「只有代码块变了」的更新机械 --apply 的 briefing 生成器。
