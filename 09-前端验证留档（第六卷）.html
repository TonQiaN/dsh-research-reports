01 · 现场

一本不在主干上的规则书

先把"前端"这个词在这个仓库里指什么钉死，顺便交代一个从一开始就该说破的反常事实。

dsh 的前端是三块：packages/client/*（40 个工作区包，其中 34 个是 ui-* 插件，另外 6 个是基础设施：runtime / connection / web / modules / hmr / locale）、packages/host/*（8 个包，浏览器的服务端半边：webserver、apiproxy、frontend-static…）、以及构建入口 apps/web。

规则书是 packages/client/AGENTS.md，150 行 / 3087 词，槽位系统、四份 props、响应式读取纪律、导出纪律、分层红线、依赖声明、模块图、目录规制、样式、测试阶梯、两个 checklist——全在这一份里。

但它几乎不在文档主干上

根 AGENTS.md（唯一被软链成根 CLAUDE.md 的文件）里 GUI / browser / frontend 出现 0 次，它的"Repository layout"块列了 35 个包组，没有 client/、没有 host/、没有 apps/。根 AGENTS.md、packages/AGENTS.md、packages/README.md、docs/ 顶层——也就是整条文档主干——里没有任何一条链接指向 packages/client/AGENTS.md；全仓唯一一条 Markdown 链接来自 docs/cookbook/adding-a-package.md 的一句附注，另有 8 处在 client 源码 JSDoc 里以纯文本形式引用它。它也不在 scripts/doc-budgets.manifest.json 的 9 个条目里，所以 3087 词无人过问——而 docs/AGENTS.md 写的 prose 目标是"子树 AGENTS.md ≤ 600 词"。

grep -ci "gui\|browser\|frontend" AGENTS.md → 0；grep -rn "client/AGENTS" AGENTS.md packages/AGENTS.md packages/README.md docs/*.md → 无匹配（docs/*.md 不递归子目录，唯一的 Markdown 链接在 docs/cookbook/adding-a-package.md:37）；wc -w packages/client/AGENTS.md → 3087；scripts/doc-budgets.manifest.json 共 9 键，无一前端。

它靠什么被 agent 读到？主要靠"就近 AGENTS.md"这个约定——agent 在 packages/client/ 下工作时会读最近的那份。也就是说，这本规则书几乎不靠链接分发，靠的是位置。这在本卷后面会反复出现：dsh 的前端治理有大量东西是"放在那儿等你走到"，而不是"被索引到"。

02 · 文档管理

五个装置

"文档管理"在这里不是一份写作规范，而是五个各管一段的装置，其中四个有闸门、一个没有。

装置一：唯一归属（one home per fact）口头

docs/web-styling.md 只有 25 行，是浏览器端样式的唯一权威——--dsw-* 令牌的归属、禁止组件库和 Tailwind、禁止在功能组件里写字面色值、禁止在功能组件 CSS 里写主题选择器。packages/client/AGENTS.md 的 Styling 段先点明"docs/web-styling.md is authoritative"并链过去，然后用一句压缩复述核心禁令（令牌归属、CSS Modules + clsx、无字面色值 / 组件库 / Tailwind、中文文案英文注释）——它示范的是"压到一句并指向权威"，而不是零复述。

这条规则本身没有任何 gate。docs/AGENTS.md 给的唯一手段是人工 grep："The same rule stated in more than one home. Grep a distinctive phrase; keep one home and link the rest."

docs/web-styling.md（25 行）；packages/client/AGENTS.md §Styling；docs/AGENTS.md "Each fact has one home: the tier whose job it is; elsewhere, link there."

装置二：决策留档 = Agent Notes 闸门

路径即元数据：{proposed|implemented|rejected}/{class}/yyyy-mm-dd-topic-title.md，class 是六选一的闭集（feature / bug-fix / simplification / architecture / process / testing）。当前英文侧 723 篇：implemented 544、archived 143、proposed 25、rejected 11。格式闸门只走三个活跃生命周期——实跑 verify-agent-note-format 报的是 580 篇（544+25+11）；archived/ 由另一条 verify-archived-agent-notes 管，它查的是三件套完整性、归档元数据、sidecar 哈希和只增不改的冻结清单。

verify-agent-note-format 硬校验：前三行必须逐字是 # Agent Note: <title> / 空行 / Status: …，且 Status: 必须与所在生命周期目录一致；body 必须以 ## Problem 开头；implemented/ 必须有 ## Decision + ## Alternatives considered + ## Consequences，并禁止出现 ## Proposal / ## Plan / ## Migration plan / ## Acceptance criteria。

## Alternatives considered 是强制的，理由写在 .agents/notes/README.md 里：

A decision recorded without what it beat invites re-litigation — the failure Agent Notes exist to prevent..agents/notes/README.md · Alternatives considered — mandatory

它带一个写明日期的祖父条款：FORMAT_ADOPTED = '2026-07-05' 之前的旧笔记，若其备选方案已无法从记录中重建，可以用一行指定注释（<!-- agent-note-format: alternatives-not-recorded (pre-format Agent Note) -->）代替该段，闸门只对这类文件放行。今天活跃树里有 16 篇在用它。这是个值得注意的处理方式——不追溯改写历史，但把豁免做成显式、可枚举、且不会扩散到新笔记的形式。

对本卷最关键的是生命周期迁移那条规则：proposed/ → implemented/ 时，## Acceptance criteria 必须被折叠进 ## Consequences，或者变成一个现在时的 ## Testing / ## Verification 段，写清"现在是什么在钉住这个行为"。留档的落点就在这里（§6 有实例）。

.agents/notes/README.md §The file format / §Moving between lifecycles；scripts/verify-agent-note-format.ts、verify-agent-note-classification.ts、verify-archived-agent-notes.ts 均为 doc-sync 的 leaf gate。

装置三：包级 README 的强制章节与顺序 闸门

verify-package-readme-model-experience 扫 packages/*/*/package.json，要求 ## Model Experience 与 ## Known Limitations and Deferred Work 是包 README 的最后两个 H2，且顺序固定（当 Limitations 段不存在时，Model Experience 必须是最后一个 H2）；README 整个缺失直接 fail。豁免是显式枚举的：4 个 model-agnostic 包不写 Model Experience，1 个包不写 Limitations，全部写死在脚本的审计表里。

纯 UI 包也躲不掉，而且短式写法要过正则 ^None, as .+\.$：

## Model Experience

None, as the reload driver is browser-side machinery; nothing here reaches a model request.

#### KV Cache effect

None; this package neither assembles nor sends a provider request.

—— packages/client/hmr/README.md。40 个 client 包里有 37 个用这种一句话短式，只有 ui-deliverables、ui-skill、ui-subagent 写了完整结构化条目。

这个设计的意思很清楚："这个包对模型不可见"是一个必须被显式声明、而不是默认省略的事实。一个前端插件也得回答"你有没有喂给模型什么"。

scripts/verify-package-readme-model-experience.ts（globSync('packages/*/*/package.json')；"must be the final two H2 sections, in that order"）；scripts/verify-package-readme-limitations.ts（全仓唯一豁免包是 packages/util/brand）。

装置四：双语配对 闸门

40 个 client 包 + 8 个 host 包，全部是 README.md / README.zh.md / README.i18n.yaml 三件套，无一残缺。.i18n.yaml 记录两侧的 git blob hash；配对 gate 不只查存在性，还比对结构签名：标题层级、代码块逐字内容、表格行列数、列表种类、链接的出现顺序。

校验跑两次：lefthook 的 pre-commit 只校验 staged 的 .i18n.yaml（快），全量在 doc-sync / CI。docs/i18n/README.md 写得很直白："The no-argument corpus-wide form is what doc-sync and CI run; a scoped green never substitutes for it at PR level."

连用户文档里的 UI 截图都是成对的——docs/user/guide/providers-models-page.png 与 providers-models-page.zh.png，中英两套界面各截一张。

注意范围边界：packages/client/AGENTS.md 不在配对范围内（scope 谓词是 README 类文件名 + docs/** + .agents/notes/** + python/** + 根级几个文件），所以它至今是英文孤本。

scripts/translation-pairing.ts（README_ARTIFACT 正则、TranslationStructureSignature 五字段）；lefthook.yml pre-commit job "translation pairing (staged records)"；find . -name AGENTS.zh.md → 无。

装置五：一部分前端文档是生成给模型看的 闸门

scripts/gen-client-catalog.ts 词法扫描 packages/*/*/src/**/*.{ts,tsx} 里的槽位声明与 slots.register 调用（不走类型检查器），生成 packages/extensions/cordis-client-runner/src/client/slot-catalog.ts——供模型通过 cordis_inspect what:"client" 工具读取。它的模块 JSDoc 把目的说得很清楚：

…every fact it needs to do that safely — which keys exist, what each register call must pass, what the component receives, who already occupies the seat, and when the seat exists at all — is decided at compile time by the shipped web bundle.scripts/gen-client-catalog.ts

生成器本身就是一道文档 gate：某个 UI 槽位声明没写 JSDoc 直接 fail，报错文案是一句写作指令——

has no JSDoc prose. Write it from the REGISTRANT's side: what to pass,
what the component receives, whom a registration replaces, and what
absence looks like (packages/client/ui-settings/src/client/contract/slots.ts
is the template).

（源码里是一整行字符串，此处按版面折行。）它甚至把模板文件的路径交给你——报错本身就是一份写作说明。

它还带 MAX_ENTRY_LINES = 120 的单槽行数预算，理由写在常量注释里：narrowing 到单个槽位就是为了少花 context，"a report a model cannot finish reading is a defect rather than a detail"。这是整个前端文档体系里唯一一条会让 gate 变红的长度限制（同文件的 MAX_DECL_CHARS = 1200 只截断不报错）——它管的不是人的阅读负担，是模型的。

scripts/gen-client-catalog.ts（OUT = 'packages/extensions/cordis-client-runner/src/client/slot-catalog.ts'、MAX_ENTRY_LINES = 120、MAX_DECL_CHARS = 1200）；verify-client-catalog = gen-client-catalog.ts --check，是 docSyncLeafGates 的一条。
这五个装置合起来是什么

一份权威文档（唯一归属）+ 一份决策档案（Agent Notes）+ 一份契约声明（README 强制章节）+ 一份翻译一致性（双语配对）+ 一份机读目录（slot catalog）。人读的那三份里，只有格式和章节被机器管；内容对不对，全靠 review。

03 · 验证

三层结构与唯一的浏览器闸门

GUI 测试被切成三层，命令被排成一条阶梯，而 CI 上真跑浏览器的闸门只有一条。

三层的划分settled 在 .agents/notes/implemented/process/2026-07-20-gui-testing-system.md，切法是"沿架构自带的测试钩子自底向上"：

铁律是 "each tier tests its own layer, upper tiers never re-test lower ones"。这条纪律该 note 自己承认没人机器管：

Inter-tier discipline remains review-owned, while Linux CI mechanically enforces browser-golden freshness.2026-07-20-gui-testing-system.md · Consequences

本地阶梯 口头

packages/client/AGENTS.md 的 "Before you push" 给了三级，要求"跑覆盖你改动的最窄那一级"：

每次改 GUI 代码
pnpm run test:gui——秒级，无浏览器无服务器。原话是"This is the inner loop; run it as freely as a typecheck."
可能改变组装输出

提 PR 前
走 dsh-pre-push-checks skill 挑最窄的一组；仓库刻意没有 repo-wide 的 pre-push 聚合。

值得记一笔：test:gui 这条被称作"内环"的命令，在 scripts/run-gates.ts、lefthook.yml、所有 workflow 里零出现——它就是 package.json 里的一行路径过滤（vitest run packages/client packages/host），完全靠自觉。client 源码仍被逐文件 100% 覆盖率闸门间接盖住，但那是另一条路，而且如 §7 所示，那条路对 client 有 51 条排除。

PR 上唯一真跑浏览器的 job 闸门

node 24 / snapshots and artifacts（node-24-consumers），仅 Linux。scripts/run-gates.ts 的 webSnapshotGate 在 DSH_WEB_SNAPSHOT_WORKERS 有值时注册 test:web:ci 并显式注入 DSH_SNAPSHOT=replay；CI 真实设置的是 6（ci.yml 里全仓唯一一处）。

严格说是"PR 上唯一"：serial / linux (self-hosted standby) 那个 job 也装 Chromium 并跑同一条闸门，但它只在推 master 时触发、且不拦合并。

04 · 留档

证据长什么样

这是本卷最该被抄走的一节：dsh 的 GUI 验证证据不是截图，是可以逐行 diff 的文本。

apps/web/tests/snapshots/ 是主证据库：64 个场景目录 / 138 个受控文件 / 约 496 KB。构成如下——

数量文件形态是什么

体裁一：归一化的可访问性树

不是像素，不是 DOM，而是浏览器 ARIA 快照经归一化后的文本。snapshots/cordis-tool-round/ui.expected.md 第 31–42 行，原样：

- button "Register Cordis Plugin snapshot noop does nothing, for the snapshot Ready" [expanded]:
  - img
  - text: Register Cordis Plugin snapshot noop does nothing, for the snapshot Ready
- tablist "Plugin source":
  - tab "Client"

它同时钉住了四件事：控件的语义角色、可访问名、展开/选中这类状态，以及缩进所表达的层级。一次 UI 改动如果动了任何一项，diff 会精确落在那一行。

体裁二：把像素测量写成人话

布局类断言不进 ARIA 树，而是单独一份 geometry.expected.md。composer-tab-geometry 的样子：

# Input card position across the Chat and Trajectory tabs

## Wide viewport (1680px, card at its cap)

- Chat: scrollbar-gutter stable, overflow hidden/auto
- Chat scroller scrolls: true
- Chat reserved band: 8px
- Trajectory: scrollbar-gutter auto, overflow hidden/auto
- Trajectory scroller scrolls: false
- Trajectory reserved band: 0px
- input card left edge moves between tabs: 0px
- input card right edge moves between tabs: 0px
- input card width changes between tabs: 0px

全文 37 行，三节：宽视口、窄视口、以及一节"把补偿去掉"的对照组——对照组里那两个 0px 变成 4px，正好证明这个断言真的能失败。

这是个很聪明的折中。三层 note 明令 app 级快照"own stable visible state … not CSS pixels"，而这里把像素先归约成一个稳定的布尔或差值，再落成人类可读的断言——"两个 tab 之间输入卡左边缘移动 0px"是稳定事实，"左边缘在 x=412px"不是。

连命名都被闸门管 闸门

scripts/check-expected-filenames.sh 用三条 pathspec（顶层 glob、递归 glob、排除 vendor/**）git ls-files 扫全树，命中就 exit 1，报错两行：check-expected-filenames: tracked non-vendor filenames must not contain "golden":，然后是 Rename each file with an accurate term such as "expected".

这条闸门是路径触发的：.github/workflows/expected-filenames.yml 的 on.pull_request.paths 只匹配含 golden 的路径，而且它是独立 workflow 文件，不在 all-checks-passed 的 needs 里（ci.yml 自己注明跨 workflow 文件够不着）。所以：一个不新增 golden 命名文件的普通 PR，这条 job 根本不会跑。设计上它是"你想犯这个错的时候才拦你"。

scripts/check-expected-filenames.sh；.github/workflows/expected-filenames.yml；git ls-files apps/web/tests/snapshots | wc -l → 138。
为什么是文本不是图

三个理由，全都指向同一件事——让证据进入代码评审流程：可以逐行 diff；可以在 PR 里被 reviewer 直接读懂；跨平台可复现（根 AGENTS.md 的原则是"Fixtures must replay on macOS/Linux; fix fixtures, not normalizers."）。截图做不到任何一条。全仓库 9 张 png——4 张用户文档界面截图、3 张 read_image 工具的测试夹具、1 张 provider 图像输入的 e2e 夹具、1 张 badge——没有一张是 UI 回归证据。

05 · 核心

教 AI 留档的六个机制

按约束力从强到弱排。前三条是被那条 CI job 执行的测试断言，第四条是技能文本，第五条是产品自己的 system prompt，第六条是一份事故报告。

机制 01 测试

三态模式，且 refresh 是期望输出的唯一 writer

浏览器证据有三种模式：record（真跑模型录制轨迹，要 key）、replay（回放已录轨迹并比对期望输出，默认，无 key）、refresh（回放并重写期望输出）。

apps/web/tests/scaffold.ts 里 compareOrRefreshGolden 的 JSDoc 把语义写死了：

Refresh is the ONLY writer: a missing golden in replay mode fails with the healing command instead of silently self-bootstrapping.apps/web/tests/scaffold.ts

实现也就这么几行——refresh 直接写文件；否则文件不存在就抛错并把自愈命令印出来（run DSH_SNAPSHOT=refresh pnpm run test:web to generate it），存在就 expect(payload).toBe(...)。replay 模式下永远不会有"文件不存在所以我先生成一个"这条路径。（record 模式也写盘，但它写的是输入侧的 session.jsonl 轨迹，不是期望输出。）

而 CI 永远只跑 replay。为什么不是"CI 跑 refresh 然后检查工作树有没有脏"？CI gate 那份 note 明确拒绝了这个方案：

checking after writing turns the assertion mechanism into a generator; if the working-tree check is wired incorrectly, it can turn a regression into a passing expected-output update.2026-07-30-web-browser-snapshot-ci-gate.md · Alternatives considered

这是整套设计里最防 AI 的一条。一个被要求"把测试跑绿"的 agent，最自然的动作就是重新生成期望值；这套设计把那条路径从 CI 上物理拿掉了，只留在本地、且需要人明确输入 DSH_SNAPSHOT=refresh。note 里对开发者的要求是：只有在确认用户可见输出确实是有意改变之后才明确选择 refresh 入口（pnpm run test:web:refresh），逐条 review 期望输出的 diff，然后再用 replay 跑一遍确认没有文件被写。

apps/web/tests/scaffold.ts compareOrRefreshGolden；scripts/run-gates.ts webSnapshotGate 注入 DSH_SNAPSHOT: 'replay'；docs/testing.md："CI forces read-only DSH_SNAPSHOT=replay, never writing expected outputs"。
机制 02 测试

证据目录的完整清单也被断言

assertFixtureInventory(dir, expected) 要求场景目录正好持有预期的文件清单——expect(entries).toEqual([...expected].sort())。多一个孤儿文件 fail，少一个证据文件 fail。它是逐场景自愿调用的：83 个测试文件里有 50 个调了它。

它还往下走一层：每个受控 .jsonl 必须是 request-header scrub 的不动点（再 scrub 一次内容不变），且不得含 run-local 的浏览器 rpcId。也就是说，录制时那些"这一次运行才有"的量必须已经被清理干净才能落盘。

这条针对的是 AI 留档的两种典型病：留一半（改了行为只更新了同场景里的一份证据文件），和留垃圾（调试时手动生成的中间文件跟着提交了）。

apps/web/tests/scaffold.ts assertFixtureInventory（"the scenario directory holds exactly the expected files and every committed JSONL is a scrub fixed-point without a run-local browser RPC id"）。
机制 03 测试

不许用固定延时当证据，不许用 substring 当判定

captureStableAria 不是"等 2 秒然后截"，而是用 expect.poll 轮询直到连续两次归一化 ARIA 快照完全相同才返回，5 秒超时，失败信息是 aria snapshot did not stabilize。

同一条纪律在 record-browser-gif skill 里被写成显式禁令：

Do not use a fixed delay as proof that the application reached the state..agents/skills/record-browser-gif/SKILL.md

还有一条更细的，专门针对聊天界面：完成判定必须匹配精确文本相等的元素，禁止 body.textContent.includes(...) 这类 substring 检查——因为用户 prompt 的回显本身就会让 substring 检查假通过。Playwright 的可访问名定位在需要相等语义时必须用 exact: true，理由同样是后代文本或 prompt 回显会造成假匹配。

skill 里甚至给了怎么制造瞬态状态来拍它：驱动一个慢的前台操作（比如 sleep 15 的 bash 命令），在同一次浏览器脚本调用里轮询一个 data-* DOM 标记并截图——因为跨工具调用的状态会在轮次结算时丢失。以及怎么让模型配合：指示它在本会背景化慢命令时留在前台，并给一个结算哨兵（"reply with the single word done"）来锚定完成判定。

机制 04 口头

GIF 技能：一个 storyboard = 一次因果执行

这是 dsh 前端治理里写得最详细、也最没有闸门的一条。skill 的 frontmatter 里就带着那句 MUST："for every pull request that changes product-user-visible GUI behavior, which MUST include a GIF recorded from the pull request's real server and model flow"。

它要求的不是"录个演示"，而是一条可追溯的证据链：

  • 钉住那棵树。要求干净工作树，git rev-parse HEAD 记录确切 commit，然后构建这棵树。"A GIF recorded against another commit's build misattributes the evidence."
  • 每次 run 用全新状态。新的 DSH_HOME / DSH_AGENTS_HOME / workspace / session，浏览器给全新隔离上下文；做不到就在导航前清掉该 origin 的 cookie 和站点存储。
  • 一个 storyboard = 一次 run。捕获失败就整轮丢弃、从新的状态根重录，绝不拼接不同 run 的帧。
  • 验证对象是编码后的 GIF 本身。不是源截图。viewer 只渲染第一帧时，要用 ffmpeg 从编码后的 GIF 解出代表帧来看——"the pre-encode screenshots do not prove the encoded order, palette, or final hold"。
  • 涉及工具调用时必须有细节帧。如果结论关于某次 tool call、拒绝或恢复，storyboard 必须包含一帧显示工具身份、状态或稳定错误码、以及下游结果。"A chat-only outcome does not prove why the tool path behaved that way."
  • 禁止替身。fixture 查询、mock transport、合成事件注入、test-only hook——一律不能冒充 real。凭据或服务器不可用时"report that limitation instead of substituting a fixture"。

写进 PR 的 provenance

GIF 旁边必须写清四件事：确切的被演示 commit SHA、服务它的 tree 和 origin、任何 mode flag 或浏览器状态例外、以及是否真的跑了模型轮次——"so reviewers know exactly what the recording proves"。用了用户已有的 Chrome 状态要声明，用了 Playwright 兜底要声明，把某个原生系统界面换成可被浏览器驱动的官方生产后端也要声明。

发布是独立的一步，且两端都要验

GIF 绝不提交到 PR 自己的分支或任何会并入长期分支的分支（二进制会污染每一次 clone），而是走一个孤儿 assets 分支（<series>-assets，无父提交、只装媒体，一个分支服务一整个 PR 系列）。推送前校验分支只含媒体、暂存 GIF 的校验和与本地已验证工件一致；推送后用已认证的 API 或 raw 请求确认远端路径、字节数、校验和、200 和 image/gif——匿名 404 不能证伪一个私仓资源。

最后这一段是本条最讲究的地方：改 PR body 之前重读一次 live head，必须仍等于记录的那个 commit；改完再读一次，还必须停在那个值上；另外把 body 交给 GitHub Markdown API 渲染，确认期望的 <img> 真的在。也就是说，"我录的东西"和"PR 现在是什么"之间的漂移被显式检查了两次。

但这条 MUST 没有任何闸门

这条 MUST 只写在那一个 skill 文件里（外加一份已归档、不再作为权威的 Agent Note）；同目录的 evidence-chain note 是它的理由书，个别特性 note 会在 Testing 段顺手提一句。但根 AGENTS.md、docs/testing.md、CONTRIBUTING.md、packages/client/AGENTS.md、PR 模板里 gif 与 screenshot 出现 0 次，全部 workflow 里也是 0（ci.yml 里 grep -ci gif 的两处命中都来自 JSON.stringify）。没有任何 workflow 读 pull_request.body 去找 GIF。

顺带纠正一个容易得出的错误结论：仓库里 .gif 数量为 0 并不是没人守规矩的证据——skill 明令 GIF 不得提交进主历史（"binary media committed there bloats the repository history for every future clone"），0 恰恰是规矩要求的状态。真正无人验证的是"PR 里到底有没有那段 GIF"。（离线 clone 看不到远端，assets 分支是否存在无法核实。）

它确实在被执行：Agent Note 里能找到引用，例如 2026-08-18-web-home-path-tilde.md 的 Testing 段结尾写着"Product-GUI PRs still record a real-browser GIF of the hover card."——但这属于"作者自己记了一笔"，不是"机器验过"。

.agents/skills/record-browser-gif/SKILL.md；.agents/notes/implemented/process/2026-08-08-browser-gif-evidence-chain.md；grep -ci gif 于上述五个文件均为 0；git ls-files | grep -ci '\.gif$' → 0。
机制 05 测试

产品自己的 system prompt 兜底

这条最有意思：dsh 的 Web 应用在装配时（当 surfaceContext 为 true——headless 与 complete-prompt 档位会关掉它）会往 system prompt 里注册一个 app:web-surface 段落，直接告诉正在这个 GUI 里跑的 agent 它自己的运行时坐标。

You are interacting with the user through the DeepSeek Harness Web GUI at ${webUrl}.
When the user refers to "this page", "this GUI", or "this app" without naming
another target, they mean this GUI.
The browser provides no implicit DOM, route, or screenshot context.
…
Starting another server does not update this GUI.
The apps/web Vite entry builds the shell but is not a standalone application
because only dsh web injects window.__DSH_BOOT__.
Do not start a replacement server unless the user asks; if one is needed, use a
managed background job and verify its exact URL.

—— packages/bundle/web-app/src/index.ts · webSurfacePrompt()

同一段还讲清了更新契约：HMR 接收器是活的，但客户端插件改动要免刷新生效，还得同一个 checkout 里同时跑着 pnpm run dev:web 在重建 bundle——"verify that watcher before promising automatic updates"；其他任何改动（shell、普通包）都得重建产物并刷新这个已有 URL 再验。同时通过 shellEnv 把 $DSH_WEB_URL 暴露给 bash。

为什么这算"教 AI 留档"？因为验证的第一个前提是知道验收目标是哪个 origin。这一段把它从"模型自己推断"变成了"模型可见的运行时事实"。它是下一条那份事故报告的直接产物。

机制 06 口头

把一次"AI 交了假证据"写成事故报告

docs/postmortem/0003-web-agent-gui-feedback-loop.md，标题就是结论："Web agent validated a replacement server instead of its current GUI"。这是整个仓库里最直接回答"怎么指导 AI 做好验证留档"的一份文件。

发生了什么

一个 agent 在 dsh 自己的 Web GUI 里跑（端口 3081），选中的 Workspace 是一个空的 test/ 目录。它改了 GUI 主题源码，然后：

  • turn 2 · seq 30939 改完主题，直接让用户"跑 pnpm run demo:tui 或者打开某个 Web 应用"——把验收甩回给用户，自己没跑任何组装级验收。
  • turn 3 · seq 31865 读了 apps/web/package.json，起了裸 Vite 在 5173，看到 HTTP 200 就宣布成功。浏览器实际抛的是 client-modules: window.__DSH_BOOT__ is missing or not an object，白屏。
  • turn 4 · seq 34309 / 34441 找到了正确的 dsh web 路径，重建 shell，用 & 在 3334 起了个无人管理的替身进程，只检查了这个替身返回 200 且有 boot manifest。从头到尾没探过 3081。
  • turn 5 · seq 34556 / 34681 用户告诉它 3081 早就显示新主题了。到这时它才去看已有进程，把多余的服务器收掉。

取证方式本身值得学：整条时间线是从持久化的会话事件日志里按序号还原的（session-3eb796c2-…，序号 6 / 30939 / 31865 / 34309 / 34441 / 34681），而不是从 agent 事后的自述里重建意图。原文写得很克制："The timeline below follows those events rather than reconstructing intent from the later report."

根因

"The Web assembly had no model-visible identity for the current GUI, canonical URL, or runtime mode." 会话 cwd 正确地标识了用户选中的 Workspace，但模型把那个项目目录当成了应用目录。没有任何持久记录把 GUI 源码 checkout、构建产物、服务进程、目标 origin、浏览器验收这五件事关联起来。

而错误路径之所以看着合法，是因为裸 Vite 返回 200——window.__DSH_BOOT__ 只有完整 host 会注入，所以传输就绪不等于应用就绪。

最狠的一句在后面：第一版回归测试犯了同一个错的另一种形式——超时杀掉 Vite 满足了"非零退出"的断言，是个假阳性；靠真实复现才把它暴露出来。

加固措施

这份 postmortem 列了五条，注意它们的形态——没有一条是"加一个检查 PR body 的 gate"：

  1. Web 启动器把 canonical loopback URL 和真实的 production/development 模式发布进 app:web-surface prompt 段和 $DSH_WEB_URL / $DSH_WEB_MODE。
  2. 生产路径的指引要求重建产物并刷新已有 URL 后再验；开发路径讲清 dsh web --dev 只挂 HMR 接收器。
  3. apps/web 的独立 Vite serve 模式在配置阶段就拒绝；它的子进程测试证明自然退出，并给 Server.listen() 打桩，让一次瞬时 bind 不能悄悄通过。
  4. 分层的真实路径测试覆盖 CLI 请求、精确的生产/开发 prompt、shell 运行时事实、同端口静态替换、源码 watcher 重建、host stat 轮询、以及页面身份不变前提下的浏览器 HMR。
  5. "PR evidence preserves screenshots from the original 3081 session and a real-model before/after GUI run; external browser, HTTP, process, and session-log observations carry acceptance."

前两条要读作"2026-07 当时的加固清单"，不是当前 CLI 表面：--dev 开关、Web 运行时的 mode 配置、分模式的 prompt 契约和 DSH_WEB_MODE 变量都已在后来的一次 cmdline 精简里删除（HMR 行现在无条件挂载），基线上只剩 DSH_WEB_URL。也就是说，这份 postmortem 的 Guardrails 段自己已经对不上代码了——恰好又是一次"没有闸门盯着的事实会漂走"。

它留给 AI 的四条验证守则（原文）

  • The agent must know hidden runtime prerequisites before it can guide the user; startup mode is application context, not tribal knowledge.
  • HTTP readiness, build success, and a boot manifest are different facts. Acceptance names the exact origin and externally observes the requested change there.
  • A replacement service cannot prove that an existing page changed. Long-running processes use managed task lifecycles when they are actually requested.
  • A regression test must be able to fail for the reported mechanism. Process timeout is not equivalent to fail-fast, and post-exit port availability does not prove the port was never bound.

06 · 模板

一份 PR 的留档长什么样

机制讲完了，落到纸面上是两个地方：Agent Note 的 ## Testing 段，和 PR body 里那个折叠块。

先看 Agent Note 侧。2026-08-18-web-home-path-tilde.md 是一个典型的小 GUI 特性（把 Workspace 悬浮路径里的 home 前缀显示成 ~），它的 ## Testing 段是逐层点名的：

Package tests cover abbreviateHomePath, toolRowModel / readCardModel home abbreviation, Workspace hover display versus copy, and host.describe schema plus live homedir(). Assembled replay apps/web/tests/home-path-tilde.snapshot.ts hovers the fixture home-descendant Workspace. Product-GUI PRs still record a real-browser GIF of the hover card..agents/notes/implemented/feature/2026-08-18-web-home-path-tilde.md · ## Testing

三句话对应三层：包级单测（纯函数 + 卡片模型 + host schema）→ 组装回放快照（点名到具体文件和具体交互）→ 真实浏览器 GIF。这就是这套体系期望的留档密度——不是"已测试"，而是"哪一层、哪个文件、验的是哪个行为"。

PR body 侧要朴素得多。.github/pull_request_template.md 全文 13 行，三个字段——关联 Issue：，加上折叠块里的两个：

<details>
<summary>变更与验证</summary>

- 变更：
- 验证：

</details>

验证那两个字段没有 checklist、没有必填项、没有任何机器校验。整套体系把"证据该长什么样"的重量全压在 Agent Note 和受控快照上，PR body 的验证栏只是个转述位。

同一份 body 的另一半倒是被机器验的：.github/workflows/issue-policy.yml 在每次 PR 事件上跑 issue-management/policy.mjs pr，正文没引用同仓库 Issue 就以 PR 正文必须引用至少一个同仓库 Issue 失败，另外还检查 kind/* 恰好一个。所以这个仓库有能力校验 PR 正文——它只是没把这个能力用在验证证据上。

怎么选该跑哪些检查

dsh-pre-push-checks skill 管这件事，它的核心立场是"除 git hooks 之外没有普适的本地基线"（hooks 本身很窄：pre-commit 修 staged lint、查空白、管翻译配对与归档笔记、重生成第三方声明；pre-push 只跑增量 typecheck）：

Every behavior change needs the narrowest available test or purpose-built check that would fail for its regression; add broader checks only for surfaces the diff actually reaches..agents/skills/dsh-pre-push-checks/SKILL.md

它给了一张"改什么 → 跑什么"的映射（包/脚本行为 → 那个 Vitest 文件；文档/Agent Note/catalog → doc-sync；模型 / 编辑器 / CLI / 终端可见输出 → 拥有该输出的那个无 key 快照或真实可运行示例场景；清单/导出/构建配置/worker 与 bin 入口/已构建运行时路径 → build + hygiene + 已构建产物冒烟；真实 provider 行为 → test:e2e），并且明确禁止两件事：不要因为接下来要 commit/push 就把一个已经通过的检查再跑一遍；不要用 --passWithNoTests、调低覆盖率阈值、或收窄 --coverage.include 来藏掉一个未被覆盖的受影响文件。

失败处理那一段直接针对 agent 的常见托辞：如果看起来是环境相关的失败，要拿出证据——记录确切命令、失败的测试、平台相关的不一致点，确认相关的非平台证据，优先修跨平台不确定性。根 AGENTS.md 里对应的一句是"report only commands run"。

08 · 拿走

可迁移的五条

如果你也在让 AI 改前端，这五条与 dsh 的具体技术栈无关。

1 · 让证据文本化

ARIA 树和"把像素归约成稳定断言再写成人话"这两种体裁都可以直接抄。判据是：reviewer 能不能在 PR diff 里读懂这次改动改了什么。截图做不到，文本可以。

2 · 把"写期望值"和"比对期望值"分成不同模式

并且 CI 只允许比对模式（replay 只读，refresh 与 record 才写，且只在本地）。这比任何写在 prompt 里的"不要偷懒"都管用——一个被要求把测试跑绿的 agent，最自然的动作就是重新生成期望值，那条路径必须在 CI 上物理消失。

3 · 断言证据目录的完整清单

不只断言内容对不对，还要断言该有的文件一个不少、不该有的一个不多。这一条治的是"留一半档"和"留垃圾"，成本极低。

4 · 给 agent 它自己的运行时坐标

把"你现在服务在哪个 URL"、"什么改动会自动生效、什么必须重建"、"起另一个服务器不会更新这个页面"写进 system prompt 和环境变量，别指望模型推断。验证的第一个前提是知道验收目标。

5 · 事故要变成 guardrail，不只是文档

0003 那份把"AI 记录了虚假验证证据"当一等事故解剖，取证到会话事件序号；产出的是一个 prompt 段落、一个配置期拒绝、一组分层真实路径测试——而不是又一条写在 AGENTS.md 里的告诫。

加一条：诚实地标注强度

dsh 值得学的还有一点：它在文档里主动写明哪条规则没人管（"Nothing mechanically enforces this rule; keep it in review."）。这比假装所有规则都一样硬要有用得多。

09 · 方法

方法与边界

怎么做的

第一轮（调研）：10 个并行 agent 分片覆盖 GUI 测试分层、web 快照机制、GIF 技能、client 静态闸门与 invariant companion、前端文档管理与预算与双语、Agent Notes 留档规则、AI 工作流技能指令、CI lane 与产物、设计与文案标准、Tool UI render intent。随后 3 个验证 agent：一个专门反驳所有"这条是机器强制的"声明（要求把脚本追溯到实际执行入口——run-gates 的 lane、lefthook、或某个 workflow job；找不到执行路径就判"未强制"），一个做证据工件普查，一个做完整性批评。

第二轮（发布前事实核查）：9 个 agent 按章节分片，被明确要求"对抗式而非确认式"——每个数字自己重算并报出所用命令，每句英文引文逐字符比对，每一条"没人管"的负面断言都要重新搜 scripts/、.github/workflows/、lefthook.yml、package.json，找不到执行路径才算成立。复核 300+ 条断言，判 15 处错误、41 处不精确（含跨分片重复）、8 处无法核验，全部已改。

被改掉的错误里，有五处会实质影响读者的判断，值得单独列出：初稿把"仓库里 0 个 .gif"当成没人守规矩的证据，而 skill 本来就禁止把 GIF 提交进主历史；初稿说 packages/client/AGENTS.md 无人链接，实际有一条 cookbook 链接和 8 处源码引用；初稿说 ## Alternatives considered 无条件强制，实际有一条写明日期的祖父条款；初稿说 PR 正文"没有任何机器校验"，实际 issue-policy 会因正文未引用 Issue 而失败；初稿沿用 note 里的"8 个 client 插件"，基线上已是 37。文中所有关键数字（35 / 40 / 64 / 138 / 110 / 83 / 723 / 580 / 50 / 26 / 0）以及那次 verify-client-domain-graph 红灯，均由我本人在证据基线上重跑核对。

边界

  • 没有远端可看。本次调研在离线 clone 上进行，看不到 GitHub 上的 PR body、assets 分支、CI 运行记录。所以"GIF 实践到底执行到什么程度"只能从仓库内的引用推断（Agent Note 里确有引用），不能量化。
  • "是否有闸门"是结构判断，不是历史判断。某条规则今天没挂 lane，不排除它曾经挂过或即将挂上。
  • 本卷不覆盖终端 UI。apps/cli 走的是另一套（含一个 PTY 用例），与 Web 侧共享 docs/testing.md 的总策略但机制不同。顺带一提：docs/testing.md 里写的 apps/cli/tests/snapshots/ 在基线上并不存在，apps/cli 下也没有任何 .jsonl——这是本次核查顺手撞见的第三处"文档比代码新"。
  • 不覆盖 Python SDK 与 ACP 侧的快照体系。ACP 侧与 Web 侧确实共用 vitest.snapshot.config.ts 这条 lane（对比规模：examples/acp-agent/tests/snapshots 有 367 个文件 / 84 个场景；Web 的那批只在 DSH_EXAMPLE_MODE=lib 时才被这条 lane 收进来）；Python SDK 走的是完全另一条——期望输出在 scripts/snapshots/python-sdk-single-exe/，由 python-runtime 那个必需 CI job 用一个 Python 脚本驱动。

证据基线 141eb6fef8（2026-08-19，dsh 0.1.0-rc.8）。文中所有文件路径与引文均相对该提交；引文为原文摘录，未作改写。
