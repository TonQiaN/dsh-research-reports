  • 他负责的是立法与执法机器：AGENTS.md、Agent Note 协议、11 个 skill 里的 8 个、41 个闸门脚本里的 28 个、全部四次结构大搬迁。

三条最贵的规矩

1. per-file 100% 覆盖率，第 2 天上线。2026-06-11 bfb034830f，团队还只有一个人。它把代码库的形状改写了：现在 packages/*/*/src 是 209,665 行，tests/ 是 246,410 行——测试比源码还多（1.18 行测试 / 行源码）。186 个源文件里有约 548 处 v8 ignore 逃生口，每一处都必须写理由。它对 AI 写的代码做的事很具体：逼作者为「不存在」辩护，而不只是产出「存在」。

2. 快照层——唯一检查「模型实际看到什么」的闸门。它的存在是因为单测曾经放行过一个坏产品（事故 0001：export default 让 Loader 丢掉了插件的 inject）。覆盖率证明行跑过了，快照证明装配好的 agent 还说同样的话。两者都要，是这个团队让 AI 写的行为变更可被 diff 审计的办法。

3. 每个包必须交一份 runtime invariant。这条规则的来历很能说明问题：闸门要求每个包发布一个 invariant 检查后，agent 用「满足闸门但什么都检测不到」的断言把它填满了——断言插件名、断言 service 方法存在、断言固定的纯函数例子。于是规则被改写成「invariant 必须断言自己拥有的关系」，并且明确规定：一个解释清楚了的空实现，才是正确答案。

「满足闸门」是 AI 的典型失效模式。一个机械要求会换回一个机械符合的答案。这个仓库的应对不是加更多要求，而是教会 agent「这里没有可查的东西」是一个合法结论——并且把这个结论也变成要写理由的。

他们给 agent 开事故复盘会

这是把 agent 的认知当成一个待修的系统在做故障管理。其他三篇事故的护栏也都沿同一条阶梯落地：散文规则 → 事故 → 可执行闸门。

人类评审被挪到哪儿去了

dsh-code-review 这个 skill 明确划了界：omit issues already enforced by a green gate（绿闸门已经覆盖的问题不要再提），然后把「机器测不出来的语义残余」列成一张清单——生命周期与并发、能力与消费者匹配、模型视角（逐字检查模型收到的提示词、工具 schema、诊断信息）、真实入口路径、测试强度。它甚至写明了闸门的极限：「a green pairing hash does not prove translation quality」「Coverage is necessary but not evidence that the scenario is correct」。

一个数字收尾：scripts/ + .github/ + 各 lint/test 配置一共吃掉了 1,400 次非合并提交（19.7%），而 54.0% 的提交碰过测试文件。五分之一的工程量在维护评审员，一半的提交在给它写证据。

为 AI 文风写的 skill

dsh-trim-cot-leakage 是这个语料库最有代表性的产物。它存在的原因是：AI 写的散文会引用只有当次会话能看到的东西——(decision 3)、(audit C2)、design §4.7、「a later PR in this stack」、「used to / no longer」这类变更叙事。2026-08-09 一次清洗扫了 763 个文件（含 168 个源文件），然后把这次清洗蒸馏成了 skill。

更值得注意的是这个 skill 的另一半：一张「什么不是泄漏」的清单——过度清洗会连同耐久事实一起删掉。这是团队在给 agent 的判断力标定量程，而不是给它一条正则。

最后一个反直觉的事实：翻译并不集中。.zh.md 的作者分布几乎和提交分布一模一样（Cui 737、Yichen Jiang 311、imccyu 292、Turtle 245、Chinesezjc 205…），因为 docs/AGENTS.md 要求改动文档的那个 agent 自己交中文对照件。而那个「扩展翻译流水线」skill 反而被设成 disable-model-invocation: true——模型够不着，因为它的编排成本比直接翻还贵。

11 / 综合

这个组织长什么形状

把前十节合起来，DeepSeek Harness 的团队不是「20 个工程师 + AI 工具」，而是一个四层结构：一个人写法律，一堆机器执法，十几个人各守一块属地，每个人下面挂着自己的 AI 舰队。

五条组织原则

  1. 先立法，再招人。覆盖率闸门、lefthook、CI 矩阵、第一条 skill 全部在头 4 天落地，那时团队只有 1–2 个人。后来加入的 22 个人不是被教会标准的，是被标准拒绝过的——验收条件从一开始就是机械的而不是社交的。
  2. 评审从人身上挪走，只留语义残余。54 道闸门吃掉可机器检查的一层，ds-review-bot 和 Codex 吃掉第二层，人只处理「机器测不出来的」那一层——并且这条分工是写进 skill 的成文规定。这才是 77% 自合并能成立的前提。
  3. 包边界是并发控制原语，不是所有权声明。226 个包、中位数 4 个源文件、78.2% 的（包，日）格子只有一个作者。边界画在人到之前，桩类型就是契约，改接口需要仲裁。
  4. 创始人的工作是把自己删掉。合并权 100% → 18%，月提交 1,639 → 334，feat: 占比 11% → 3%。他把自己从实现者转成了立法者，然后连守门也交了出去。
  5. 每个人是一个「人 + 舰队」的复合单元。组织的真实并发度不是 24，是 24 × 每人挂着的 agent 数。missions/ 记录的是 9；Tianyi Cui 的 codex/ 分支并发峰值是 45。这一层在任何组织图上都看不见，但它决定了 226 个包为什么是合理的分片数。

三个代价，也要说清楚。（1）单点：发版 19/19 是一个人，Windows 全靠一个人，前六周合并权全在一个人手上。（2）记录蒸发：唯一一份第一人称的 AI 管理记录被计划性删除，团队自己的操作经验只剩下被提炼过的规则。（3）文档税：46.7% 的文件改动是文档，五分之一的提交在维护评审机器——这些成本在一个 agent 干活的语境下被明确判定为「不算成本」（“a lot of work” is not a cost argument when agents do the labor），但在人写代码的团队里它就是成本。

12 / 迁移

按你的规模抄什么

这套东西里有一部分只在「代码主要由 agent 写」时才成立。下面按规模拆开：什么现在就能用，什么要等团队变大，什么不要抄。

一个人 + 你的 agent

  • 抄「规则要有非零退出码」。不用 54 道。先挑三条你反复口头提醒 agent 的事，各写一条会失败的脚本，塞进 pre-commit。口头约定对 agent 的约束力接近零，退出码是 100%。
  • 抄根指令的词数上限。给你的 CLAUDE.md / AGENTS.md 定一个数（1,500 词是他们试出来的），超了就把内容推进分层文档并留链接。这个仓库花了 23 天涨到 8,619 词才发现不可用。
  • 抄「决策记一篇，不改根文件」。Agent Note 的核心不是格式，是「问题 / 决定 / 考虑过的替代 / 后果」四段和一句 Status:。它让你三周后能回答「当初为什么不那么做」。
  • 抄规则 7a。「未答问题不得代答」——你离开键盘时，agent 可以在已决定的范围里执行，但不许替你做新决定。这条是他们用一次事故换来的。
  • 抄「验证世界，不验证 agent 的自述」。让检查去读外部状态（文件、进程、HTTP、日志），不要读 agent 自己的输出。他们第 4 天就写下了「关键词探针会让一个作弊的 agent 过关」。
  • 暂时别抄：per-file 100% 覆盖率、双语配对、724 篇 Note、快照层。这些的维护成本要有产出体量才摊得平。

2~5 人

  • 先切边界，再分人。这是最可迁移的一条：把要做的东西切成足够细的模块，先把空骨架和类型桩建出来，再分配。类型桩就是契约，两个人（两个 agent）之间不用读对方实现。
  • 一个人一块属地，改别人的地方先报备。不用锁，用约定 + 精确到文件的 git add。他们的教训是：同一个包塞两个 agent 必然反复混刀，而修法是社交的（pathspec 精确、回执、不改写共享分支），不是技术的。
  • 接口仲裁只归一个人。并行写实现可以自由，但改接口必须收口到一个节点，否则并发就变成了互相拆台。
  • 让 CI 当第一评审者，人当第二。明确写下「绿闸门覆盖过的问题不要再提」，把人的注意力赶到生命周期、并发、模型视角这些机器测不出的地方。
  • 约定分支前缀。他们没约定，结果同一个工作流有三种写法（worktree/、worktree-、三种 worktree 根目录）并存两个月。花五分钟定一次，省很多考古。

5~10 人以上

  • 合并权要有明确的交接计划。他们的曲线（100% → 18%，三周）是健康的，但那三周是被人数逼出来的，不是排期出来的。提前想清楚第二个守门人是谁、守哪一半。
  • 为「产出的一半是文档」做预算。如果你要求每个非平凡改动都带决策记录 + 双语，那 46.7% 的文档改动占比就是你会得到的数字。要么接受，要么砍掉双语这一项（它是这里最贵的一条）。
  • 给 agent 开事故复盘。当 agent 的行为造成了事故（验错了服务器、把 UNKNOWN_TOOL 录成了通过的 golden），按事故报告写：根因、护栏、可执行的回归。他们四篇报告里有两篇是这个形态。
  • 不要抄「删掉自己的操作记录」。这是这个仓库最可惜的一处。第一人称的 AI 编队经验没有第二个来源，删了就只剩被抽象过的规则。

一句话

  • 规模小的时候，抄闸门和词数上限；
  • 规模中等的时候，抄先切边界再分人和接口仲裁独占；
  • 规模大的时候，抄合并权交接和给 agent 开复盘会；
  • 任何规模都别抄的：把自己的操作记录删干净。
13 / 局限

诚实的部分

  • 雇佣关系是推断，不是事实。只有 10 个人用 @deepseek.com。其余全是个人邮箱，git 无法区分「员工用私人账号」和「外部协作者」。标题里的「DeepSeek 员工」是通俗说法，本文正文一律只说「提交者」。
  • git 记录点击，不记录评审。「77% 自合并」不等于「77% 无人审」。ds-review-bot 和 Codex 的评审只在提交消息里留下回声（100 / 66 条），真正的评审线程在一个够不到的内部仓库里。所有关于「谁审了谁」的推断都到此为止。
  • 舰队规模不可观测。零 AI 协作者尾注是成文政策（missions/conventions.md 第 4 条）。分支前缀是唯一的替代遥测，而它一半是工具、一半是个人品牌（xtr/、agent/ 就不是工具）。把前缀当工具普查会凭空发明出第五家 AI 供应商。
  • 「创建了 N 个包」这类数字极易被扫荡污染。本文所有包级归属都剔除了 >40 文件的提交；未剔除时 Tianyi Cui 的建包数会从 34 虚高到 114。同理，--full-history 不加会让 .github/ 的提交数从 251 掉到 16。
  • 八月是残月。观测窗口止于 2026-08-19，八月只有 19 天。所有「八月下降」的结论都已按天归一过，但「某人 08-13 之后停了」和「某人休了一周」在这个窗口里无法区分——kingwl 的「08-04 停更」就是 git log 按提交日期排序造成的假象，他真实的末次提交是 08-11。
  • 这里是镜像仓库。合并标题写的是 from deepseek-harness/<branch>，而 README 指向 deepseek-ai/deepseek-harness。开发发生在一个私有组织里，2026-08-13 的公开只是把结果镜像出来——PR 编号、评审线程、issue 全部无法解析。
  • 这份报告被对抗性校对过。两轮多 agent 调研（15 份人物档案 + 7 个横切主题）之后各跑了一轮专门找茬的复核，共推翻约 40 处数字/归属错误（最大的一处就是上面的「114 个包」）。所有修正已并入正文，但校对本身不是穷尽的。
14 / 方法

方法

证据基线：141eb6fef8（0.1.0-rc.8，2026-08-19），完整克隆。开工前先跑了 git rev-parse --is-shallow-repository——浅克隆会让边界提交看起来像一次「凭空生出整棵树」的巨型提交，这是个非常诱人的假故事。

  1. 先手工建底盘：别名归并表、7,090 条非合并提交的全量 --name-only 解析、按人/按月/按包/按小时的交叉统计、1,054 个合并提交的作者对照矩阵。所有出现在正文里的数字都在本机重跑过。
  2. 两轮多 agent 扇出：15 个人物档案 agent（结构化 schema：任期 / 体量 / 属地 / 签名工作 / 设计权威 / 工具签名 / 怪癖）+ 7 个横切主题 agent（治理、工具签名、发布与 CI、双语文档、missions 账本、康威定律、工作节律）。
  3. 对抗性复核：每轮后接 2–3 个专门反驳的 agent，任务是把每个数字重新推导一遍、把每个「角色/意图」断言标为不可证。它们找出的问题里，最有价值的一类不是算错，而是口径漂移——用已经死掉的旧路径统计、把改名扫荡算成建包、把提交消息全文和标题混着数。
  4. 关键结论亲手复算：合并权周曲线、77.0% 自合并、AGENTS.md 词数曲线、PR 尺寸分布、（包，日）单作者率——这几条是全文的承重墙，全部由我自己的脚本独立产出。
