01 · 定义与边界

三个「skill」，一份目录：这一卷研究的是哪 11 个

在这个仓库里，「skill」这个词同时指三样东西。先把边界画清，后面的数字才不会串。

第一样是产品能力：packages/skill/ 下的四个包（skill、skill-badge、skill-filesystem、tool-skill）让 dsh 这个 agent 运行时能发现、展示、加载技能。第二样是产品自带的技能：apps/cli/config/agent-presets/cordis/skills/ 里的两份（cordis-plugin-development 3,104 词、editing-cordis-compositions 1,929 词），是 dsh 运行 cordis 预设时给自己的模型读的。第三样才是本卷主角：.agents/skills/ 下的 11 份 SKILL.md——写给在这个仓库上干活的编码 agent（主要是 Codex 和 Claude Code）读的开发流程剧本。全仓库共 16 份 SKILL.md：11 份流程 skill、2 份产品预设 skill、3 份快照测试 fixture。

03 · 起源

出生顺序：每一份都对应一次疼痛

建仓第 3 天就有了第一份；此后每一份的诞生提交、落地 PR、分支名和当时的「疼痛」都能在 git 里找到。

仓库的第一个提交在 2026-06-10。第一份 skill 出现在第 3 天，最后一份在第 60 天。11 份里有 8 份挤在 06-29 到 07-26 这四周里，几乎每周两份；之后只在 08-09 又添了一份。把每一份的诞生提交、落地 PR、分支名和当时的「疼痛」放在一起看，会看到一个反复出现的模式：先做一次痛苦的清扫或迁移，再在同一个 PR 里把方法蒸馏成 skill。

13 · 给你的

抄什么、别抄什么：三种规模下的 skill

这一节是写给正在从个人 vibe coding 走向团队的你的：哪些是写法、哪些是这个团队的规模才需要的机器、哪些只因为写代码的是 agent 才存在。

先说这一节的立场：下面是从证据推出来的建议，不是仓库自己说的；标了「意见」的地方就是意见。另外先给一个总的判断：这 11 份是一支约 25 人（37 个 git 作者名合并别名后，第二卷口径）、65 天合并 984 个 PR、代码主要由 agent 写的团队的产物，直接照搬会给一个五人小组塞进近两万词的上下文，其中一半在讲你根本没有的工具（gh stack、VitePress、翻译配对、归档验证器）。该抄的是写法和几条句子，不是文件。

三种规模

单人 + agent

先抄两份、一张清单

  • 一份 300 词的 pre-push skill：看 diff、挑「会因这个回归而变红的最窄测试」跑一次、「不要 push 然后指望 CI 结果不一样」、push 完核对远端 == 本地 HEAD、只汇报真正跑过的命令。不要抄 gh stack sync 那两节。
  • 一份 code-review skill 的 v1 形态（472 词就够）：几条「权威来源」链接 + 五条「先看哪里」+ 一段「怎么回应评审」——v1 的原话是「Technical, specific, non-performative — no "great catch", no "you're absolutely right"」，后来写成「逐条核实、在技术层面修或驳、不表演性附和」。你让 Claude 和 Codex 互相评审时尤其需要这段。
  • 一张自己的「病历」：第 8 节的写法——每被 agent 坑一次，就写一句 never／do not 进 skill，并写清「因为」。你的版本会不一样，但机制一样。
  • 把「Sources of truth（read, don't re-summarize）」当习惯：skill 里链接你的 CLAUDE.md/AGENTS.md，不复述。
  • 意见：不要在这个阶段写 prose-standard 之外的任何文档 skill；也不需要 openai.yaml、闸门、Agent Note。
2–5 人

把「怎么干」从手册里搬出来，让两家工具读同一份

  • 当 CLAUDE.md/AGENTS.md 里某一段变成了流程而不是事实，就把它挪成 skill，手册里留一句 + 链接（这是 Claude Code 官方文档给 skill 下的定义，也是这个仓库 07-22 对 pre-push 做的事）。
  • 目录放一处、软链接给另一家；如果有人用 Codex、有人用 Claude Code，这一招立刻省掉双份维护。
  • 加「guidance, not a script/checklist」；加结尾的汇报义务（报告范围、改了什么、留了什么、实际跑过什么）。
  • 加一份 prose-standard 的最小版：3 组 Over-trimmed／Balanced／Over-detailed 例子 + 「A smaller word count alone is not an improvement」+ trim-cot-leakage 的「一个测试」（站在 HEAD 的读者能否解析每个引用）。agent 写的散文最容易在这两处出问题。
  • 给 skill 上一道最便宜的 CI：链接有效性。其他闸门按疼痛加。
  • 意见：stacked PR、翻译、网站投影、GIF 证据链、归档——一个都不要提前抄；等真的开始 stack、真的有第二语言读者、真的有看不到分支的 GUI 评审人时再说。
5–10+ 人、agent 写大部分代码

这时候仓库里的整套才开始划算

  • 把「为什么」搬进 Agent Note、让 skill 用「X owns Y」链接过去；skill 只留动作与判断标准。
  • 用带字数的校准例子（archive skill 那种）和「Leaked → Fixed」对照（cot skill 那种）代替形容词——尤其当判断要交给不同的模型和不同的人。
  • 给手册设字数上限、让 skill 当溢出区；但也要定期审 skill——它们没有预算，会一直长；找一次「一个事实一个家」的重复（第 10 节那四处就是例子）。
  • 把「skill 里成熟的检查项升格进 AGENTS.md」当成常规动作（07-19 的 promote review principles）。
  • 意见：私有的评审意见挖掘工具不值得抄——它的公开记录是一次试跑、0 候选、单点维护者；先把「人在评审里说了什么 → 手动写进 skill」这条路走顺。

只因为「写代码的是 agent」才存在的东西

如果你的团队 agent 只写一小部分代码，下面这些可以晚一点：dsh-trim-cot-leakage 整份（人不会把「(decision 21)」写进 JSDoc）；prose-standard 的「require an explicit scope … do not infer a repository-wide scope or begin an interview」输入协议；pre-push 里的反作弊句（--passWithNoTests、降阈值、缩 include）和「Report pending checks as pending」；code-review 里的「rather than … trusting an agent's report」「a hand-mounted plugin does not catch invalid Loader exports」（来自事故 0001）；record-browser-gif 的「Never substitute fixture queries, mock transports, synthetic event injection」；archive skill 的「Do not archive toward a quota」。粗略估计，11 份里约一半的句子属于这一类。它们不是坏东西，只是它们的对象是模型。

三个可以直接抄的写法

1 · description 当触发器写

「Use when …」开头；把用户会说的原话放进去（「improve the docs」「this doc is too long」「stacked PRs」）。这决定了 skill 会不会在对的时候被加载。别写摘要。

2 · 反古德哈特句

凡是 skill 给出了一个可度量目标（更少的词、更多的候选、绿灯），就在旁边写一句它不许怎么达成：「Do not archive toward a quota」「do not manufacture edits to satisfy a deletion target」「Do not port duplicate or lower-confidence proposals just to preserve the count」。

3 · 命令逐字 + 汇报契约

命令写进 fenced 块，不描述；结尾写清要报告什么、并禁止过度宣称（「Report pending checks as pending」「Do not claim archived outbound links are valid」）。评审者拿到的就是这份报告。

一个最小 skill 的骨架（照这 11 份的公约数）

---
name: my-pre-push
description: Use before pushing, force-pushing, or claiming
  "checks pass" on a branch in this repo.
---
# Pre-push checks

**This skill is guidance, not a checklist.**

## Sources of truth (read, don't re-summarize)
- CLAUDE.md § Commands · docs/testing.md

## Workflow
1. `git status --short --branch`; find the live base; `git diff --name-only <base>...HEAD`
2. For each behavior change, run the narrowest test that would fail
   for its regression. There is no universal baseline.
3. Docs changed → run the docs gate. Model-visible output changed → the snapshot.

## Never
- Do not push and hope CI differs.
- Do not use --passWithNoTests or lower thresholds to hide a file.
- Raw --force is never allowed; use --force-with-lease=<branch>:<oid>.

## Report
List the commands actually run, their results, and pending checks as pending.

这份骨架的每一句都能在第 4、6、8 节找到出处；它不到 150 词（约 135）。这个仓库同名的那份 1,156 词——差额就是 gh stack、change-scope、覆盖率范围选择和三次策略翻转留下的沉积。

别忘了这些成本

  • 上下文税：11 份 description 合计约 550 词、每次会话都进索引；整份 SKILL.md 加上它要求先读的「权威来源」，dsh-code-review 一次要读约 9,900 词（≈ 1.4 万 token，双语 PR 再加 3 千词；第 12 节有账）。这个团队自己就因为这笔账把 translate-docs 关成了手动。
  • 没有闸门的规则会变成一纸空文：「MUST 附 GIF」没有任何机械检查；CoT 引用规则的笔记自己写「no gate rejects a new ordinal citation — review owns the rule」。你抄一条规则时先问：谁来拦？
  • skill 也会陈旧、也会重复：第 12 节列了这个仓库里的实例。skill 需要和文档一样被 review。
  • 单点：72% 的 skill 提交出自一人、90%（63/70）的落地合并由同一人按下。skill 是团队记忆的一部分，但这里的记忆主要由一个人书写。
