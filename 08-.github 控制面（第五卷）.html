01

四层结构

GitHub 的 .github/ 是一个约定目录：放在这里的文件会被 GitHub 平台本身读取并赋予特殊行为——workflows/ 下的 YAML 会被 Actions 执行，ISSUE_TEMPLATE/ 会变成开 Issue 时的选项，dependabot.yml 会驱动依赖机器人。它不是普通源码目录，而是这个仓库对 GitHub 平台的配置面。

deepseek-harness 用满了这个约定，并且按职责分成四层。理解这四层，就理解了整个目录：

1 个文件 · 891 行

主闸门

ci.yml。每个 PR 都跑，完全无密钥，对外只暴露一个稳定的必需检查 all checks passed。它是全目录改动最频繁的文件，占 251 次提交里的 176 次。

7 个文件

专项验证

需要密钥、需要特定内核、或只在特定路径变更时才有意义的检查，各自独立成文件：真实 API e2e、E2B 云沙箱、第三方 provider、真内核沙箱证明、原生 Landlock、文件名不变量、文档站部署。

5 个文件

发布流水线

四条互不共享版本线的发布序列：226 个 dsh npm 包、9 个 vendored 框架包、3 个原生 addon 包、2 个 Python wheel 分发。全部是「无凭据打包 → 人工触发 → 受保护环境审批」。

14 个文件

协作治理

5 个 Issue 模板 + PR 模板 + Dependabot + 一个 706 行的策略引擎（issue-management/policy.mjs）及其 413 行测试，由两条 workflow 分别以「只读判定」和「写入执行」两种身份调用。

第五层是目录自己的说明书：.github/AGENTS.md，全文只有一段，讲的全是 Windows CI 的三态拓扑。这个仓库主要由 coding agent 开发，每个目录都有一份给 agent 看的就地约定。

汇总 job 里那行承重的 always()

这个 22 行的 job 是整套设计的支点，而它的正确性系于一个容易写错的细节：

if: always() && github.event_name == 'pull_request'
needs: [node-24, node-24-coverage, node-24-consumers, node-compat,
        python-sdk, python-runtime, windows]
steps:
  - if: contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled')
       || contains(needs.*.result, 'skipped')
    run: exit 1

没有 always()，依赖失败会让这个 job 被跳过，而 GitHub 把「跳过的必需检查」算作通过。也就是说漏掉一个单词，整套分支保护会在最该拦的时候静默放行。这条注释从 2026-07-08 引入这个 job 时就写在文件里。

三个 Linux job 的分工

为什么是三个而不是一个？因为它们对「构建产物」的依赖不同：coverage 只吃源码，不需要等 build；consumers 拥有整条流水线唯一的一次 Linux 构建，然后在同一棵树上并发喂给 lint、运行时兼容、快照重放、文档 typecheck 和全部产物消费者；static 两者都不需要。三者拆开，是为了让它们能各自独立进入 runner 分配队列——这一点是在 07-30 用一次真实的排队数据换来的，见 §8。

两个可以一分钟拨动的开关

三个必需 Linux job 的 runs-on 不是常量，而是表达式：

runs-on: ${{ vars.DSH_CI_FAILOVER_LINUX == 'selfhosted'
       && github.event.pull_request.user.login != 'dependabot[bot]'
       && fromJSON('["self-hosted","linux","x64","vm-backup"]')
       || 'dsh-ubuntu-24-04-16core' }}

它解的是一个真实的死锁：当企业 runner 池降级时，每个 open PR 的必需检查都起不来，而「合一个修复」这个常规补救本身就卡在跑不起来的必需检查后面。所以开关必须是不需要合并的仓库状态——任何有写权限的人改一个仓库变量再 re-run 即可。DSH_CI_FAILOVER_LINUX 和 DSH_CI_FAILOVER_WINDOWS 是两个独立变量，因为两个平台的池会各自出问题。

配套设施

光有开关不够——切换目标必须被证明是活的。所以每次 master push 都会在自建池上跑 serial-linux-selfhosted 和 serial-windows 两条完整的、不分片的、单 worker 串行演练。它们不阻塞任何 PR，唯一职责就是持续回答「真出事时那个池接得住吗」。这也是顶层 concurrency 唯独豁免 push 的原因：演练比 master 合并间隔还长，无条件取消会让它永远拿不到结论。

04

为什么是 15 条 workflow 而不是 1 条

拆分理由在这个仓库里是写下来的，不是事后归纳的。sandbox.yml 文件开头第一句就是：

A separate workflow from ci.yml because the axis is different —
these jobs fan out over OS×runner (kernel capabilities), not node versions.

归纳起来，一个信号会被赶出 ci.yml，只有四个原因：

  1. 要密钥。ci.yml 必须无密钥可 fork。e2e.yml（DeepSeek 主 API）、e2b-e2e.yml（E2B 云沙箱）、pi-ai-provider-e2e.yml（Azure OpenAI + Anthropic）三条各自持有不同的密钥集。四个 secret 全部遵守 _EXTERNAL 后缀命名约定。
  2. 轴与 Node 版本正交。sandbox.yml 按 OS×内核能力扇出，landlock-run.yml 按 CPU 架构扇出，build-exe-for-python-sdk.yml 按目标平台扇出。塞进 ci.yml 的 node 矩阵只会做无意义的笛卡尔积。
  3. 成本或触发语义不同。花第三方 token 的、开云沙箱的、一次产出 300MB 产物的，一律只挂 workflow_dispatch，绝不 per-commit。
  4. 需要额外权限。docs-pages.yml 要 pages: write + id-token: write；issue-lifecycle.yml 要现场铸造的 GitHub App token。这些权限不该出现在主 gate 上。

一条反复出现的纪律：跳过必须是可见的跳过

这个仓库的测试大量使用「没密钥就自跳过」的模式，这在本地是对的。但它制造了一个特定的失败形态：CI 上全跳过，然后报绿。所以每一条专门为这类测试而存在的 workflow，都带一个 preflight 步骤，缺密钥时硬失败而不是跳过：

e2b-e2e.yml 注释原文：
The tests self-skip locally when the credential is absent.
A manually dispatched run must fail instead of reporting an all-skipped green.

同一条纪律在四个文件里有四种写法：e2e.yml 用单变量判空；pi-ai-provider-e2e.yml 用间接展开累计 missing 后一次报全；sandbox.yml 断言输出里出现 Test Files N passed；landlock-run.yml 用 NALR_REQUIRE_LANDLOCK=1 让运行时自己拒绝降级。

两个小 gate 值得单独看

expected-filenames.yml 只有 26 行，作用是禁止仓库里出现含 golden 的文件名（一律叫 expected）。有意思的是它的触发条件——大小写穷举的 path 过滤：

paths:
  - '*[gG][oO][lL][dD][eE][nN]*'
  - '**/*[gG][oO][lL][dD][eE][nN]*'
  - '!vendor/**'

只有当 PR 真的碰到含 golden 的路径时才会起一个 job，其余时候零常驻成本。一条纯人肉命名约定，被做成了几乎不花钱的机器门禁。

e2e.yml 则藏着全目录唯一一处对 GitHub 平台自身行为的兜底注释：

Note: scheduled triggers are auto-disabled after 60 days of repo inactivity;
push/pull_request/workflow_dispatch act as backstops.

它同时挂 schedule（00:17 UTC，注释说明是为了避开整点 cron 拥堵）、push、pull_request 和 workflow_dispatch 四种触发，不是冗余，而是对「GitHub 会在仓库 60 天无活动后自动停掉 cron」这条平台行为的显式补偿。

05

发布面：四条互不耦合的序列

仓库里有四类可发布物，它们的版本基线、变更频率、构建要求都不同。走一条流水线意味着「每次产品发布都重新发布框架和原生二进制」，所以它们被显式设计成四条独立序列：

序列包数版本线tagworkflow认证
dsh 家族226全部共享一个版本dsh-v*release.ymlNPM_TOKEN
vendored 框架9每包一条独立版本线vendor-<pkg>-v*release-vendor.ymlNPM_TOKEN
原生 Landlock3三个 manifest 共同持有landlock-run-v*landlock-run-release.ymlNPM_TOKEN
Python 分发4 wheel由根 package.json 转 PEP 440python-v*python-release.ymlTrusted Publishing

四条线共享同一个形状，而这个形状本身就是设计：

release.yml:123-124
There is no build step: publication uploads the bytes the pack job produced.

无凭据的 pack job 在每个 PR 上都跑（所以打包本身永远是被验证过的），产物存成 artifact；publish job 只在人工 workflow_dispatch 且 publish: true 时运行，跑在受保护的 environment 里，只上传 pack 出来的那批字节，不重新构建、不重新打包。

幂等性不是靠「记录这次发了什么」实现的，而是靠逐个 tarball 比对 registry 的三态：本地 sha512 与 npm view <pkg>@<ver> dist.integrity 相同就跳过、缺失就发布、不同就失败。所以重跑同一个 artifact 永远安全。

版本号只有一个真源：仓库里的 manifest。release:bump 是本地命令，把版本写进 manifest 并连 lockfile 一起提交，tag 由人在合并后打。CI 全程只读，不需要 write 权限。

Python 那条线还多一层不可逆约束：PyPI 上传立即公开、文件名不可替换、不是原子操作。所以三个平台的 runtime wheel 必须先于 SDK wheel 上传（SDK 精确 pin 同版本 runtime），而且两个 publish job 都不 checkout 源码、不重新构建，只消费同一次 run 里校验过的 SHA256SUMS。

当前状态

dist-tag 规则跨线一致：版本号里含 - 就发 --tag next，否则 latest。当前 dsh 家族是 0.1.0-rc.8，所以它进不了 latest。仓库里目前只有两个 tag：dsh-v0.1.0-rc.7（08-17）和 dsh-v0.1.0-rc.8（08-19）。

06

治理面：一个 706 行的策略引擎

.github/issue-management/policy.mjs 是这个目录里最不寻常的东西：一个零依赖的单文件 Node 程序，把「Issue 元数据规范 + PR 标签分类法 + Issue↔PR 关联 + 看板状态流转」全部实现成可执行、可单测的规则。它只接受两个子命令。

它的核心设计是一份规则、两种失败语义：

  • policy.mjs pr 由 issue-policy.yml 调用（只读权限），把错误写成 ::error:: 注解并抛出，让必需检查变红、挡住合并。
  • policy.mjs lifecycle 由 issue-lifecycle.yml 调用（GitHub App token），把同一批错误折叠进一条带 <!-- dsh-issue-policy --> 标记的机器人评论；问题修正后自动删除该评论。

规则只有一份，压力分级由调用点决定：PR 阻塞合并，Issue 只提示。

两条安全设计

两个 workflow 的第一步都叫 Check out trusted policy，都带 ref: ${{ github.event.repository.default_branch }} 和 persist-credentials: false。也就是说永远执行 master 上的策略——一个外部 PR 无法通过修改自己分支上的 policy.mjs 来豁免自己。

其次是凭据分离：只读判定用 github.token 且三项权限全 read；写入执行的权限来自现场铸造的、限定单仓库的 GitHub App token。这两条 workflow 也是全仓仅有的三处把 action 钉死在 40 位 SHA 上的地方。

看板是事件驱动的投影

状态流转规则就是一个数组的下标：Inbox(0) → Backlog(1) → Ready(2) → In progress(3) → In review(4) 单调前进，Done 和 No action 被剔出序列因而不可被自动化触碰。唯一允许的后退是「收到 changes-requested 评审」，而且带护栏——只有当目标 Project 的最新状态事件是由配置的 lifecycle actor 写入时才可回退，人手动挪过的卡片不会被机器人推回去。

这个「后退」是 08-10 才补上的。最初版本（08-04）是纯单调前进投影，缺陷很快暴露：作者改完代码重新求评审后，早先的 CHANGES_REQUESTED 仍然生效，Issue 会卡在 In review，而实际上作者正在实现修改。

一条被真正实现的排版法则

PR/Issue 正文规定「外露内容 ≤ 50 单位 + 必须有默认收起的 <details>」。这不是模板里的口号——policy.mjs 里有一个手写的 <details> 配对扫描器，和一个计数器：用 \p{Script=Han} 计汉字、用正则计西文与代码 token，并在计数前剥掉图片、两种链接、自动链接、HTML 标签与实体。

为什么要手写这一套？因为 Issue 模板用的是 legacy Markdown front-matter 而不是 GitHub Issue Forms。Issue Forms 本可以用结构化字段直接保证排版，无需事后校验；选了自由文本的 .md，就只能在事后用扫描器审计。模板形式决定了强制手段。

时间线：四个时期

251 次非 merge 提交的月度分布极不均匀：6 月 23 次 / 7 月 162 次 / 8 月 66 次。7 月一个月占了全部的 65%。

2026-06-11 · 23 次提交

创世：一个 65 行、单 job 的 CI

仓库根提交的第二天，86955b96a4 就把全量 gate 矩阵搬进了 Actions。首版只有 59 行、包管理器还是 yarn 4，一个名叫 checks 的 job 在 node 24/26 矩阵里串行跑完 install → constraints → lint → typecheck → test:coverage → hygiene → build → demo smoke。

commit message 写明它跑的是「the same commands the local scripts and git hooks run」。理由记在 Agent Note 里：这个仓库主要由 coding agent 开发，而 agent 遵守「能非零退出的命令」远比遵守散文约定可靠。第一天就带上了逐文件 100% 覆盖率闸和一个真跑 agent 的端到端冒烟。

整个 6 月只有一个文件在长（65 → 104 行），增长全部来自往同一个 job 里追加步骤。直到 06-19，因为「密钥不能进 keyless 工作流」这条安全线，才分裂出第二个文件 e2e.yml。

09

支配这套设计的原则

这些不是我归纳的，是 .agents/notes/ 里 41 篇相关 Agent Note 明确写下来的。每一条都能追到出处。

关于「什么该被机器守住」

  • 本地只跑最窄证据，CI 独占穷举。pre-commit 只做 staged lint，pre-push 只做 typecheck；「CI owns exhaustive coverage, built-artifact checks, and the platform matrix」。这条边界被正面挑战过一次（让 pre-push 跑完整 primary gate），当天回滚。
  • 闸门优先于散文约定。因为主要由 agent 写代码，而 agent 遵守能非零退出的命令远比遵守文档可靠。
  • 误配置要响亮失败。缺密钥就硬失败，不许静默跳过；旧标签显式拉黑，不许静默忽略。

关于「怎么证明 CI 自己是对的」

  • 优化后的 job 清单不能自己当自己的完备性 oracle。所以额外养一套完全不分片、串行、跨三平台的参照跑。
  • 性能目标是观测值，不是取消死线。从完成态时间戳事后测量并作为「测量结果」报告，绝不编码成 timeout-minutes；timeout 只用来兜住卡死。
  • 拓扑与并发的每一次改动都要有完成态测量支撑。「一个未完成的运行越过某个任意的耗时刻度，不构成提高并发的证据」。

关于「可用性」

  • 必需 gate 必须可移植。「计费健康、runner 处于 Ready、很大的自动伸缩上限，都不能证明一个具名池子真能接到 job」。
  • 恢复开关不能需要合并。否则会死锁在「修复本身跑不起来」上。
  • 要么进 needs，要么独立报告——绝不用 continue-on-error 把红变绿。那会让一个 gate 失败后的检查看起来成功；保留普通的独立 job 才能保住诊断结论。

关于「不要养第二套东西」

  • 并行度往 job 内部加，不往 workflow 里加。删分片时连选择器脚本一起删，因为「一条没人走的诊断路径不能把第二套 CI 架构养起来」。
  • 编排逻辑从 YAML 拉回仓库。YAML 里那 39 行手写的后台任务 + pid 收集，被换成一行 pnpm run check:ci:consumers；同一份 gate plan 在 GitHub 和开发机上是同一个调度器、同一份日志格式。
  • 源码平面与制品平面不混。CI 跑构建后的 lib/（plain Node + 真实 package exports），发布只消费 pack 出的字节。

诚实的另一面

上面九节全是这套设计做对的地方。下面是同样有据可查、但通常不会出现在介绍里的部分。

这套 CI 在公开仓上几乎不运行

公开仓 deepseek-ai/deepseek-harness 创建于 2026-08-13，MIT，约 17.5 万 star、1.9 万 fork。但它的 Actions 记录只有 08-13 那一天的 5 次 push 触发，此后只剩 Dependabot 每天定时跑。而其中最关键的那条：

".github/workflows/ci.yml"

社区健康文件全缺

.github/ 的另一半经典职责——社区健康文件——在这里是空的：没有 CODEOWNERS、SECURITY.md、CODE_OF_CONDUCT.md、SUPPORT.md、FUNDING.yml。CONTRIBUTING.md 和 LICENSE 在仓库根而非 .github/。ISSUE_TEMPLATE/config.yml 更是明确写了 contact_links: []——不给任何外部求助入口。对一个 17.5 万 star 的项目来说，这个反差很大，但和上面两条是自洽的：它没打算在 GitHub 上接受外部协作。

仓库根有一个 .gitlab-ci.yml（5618 字节），是一套与 .github 并行的第二发布系统：只在 python-v* tag 上运行，用自建 runner 产出与 python-release.yml 完全相同的 4 个 wheel，做同样的 GLIBC 断言，最后推到内部 PyPI registry。只研究 .github 会漏掉 Python 发布的另一半。

方法与一个陷阱

这份报告的每个数字都可以在本地复跑。但有两个坑会让你算出完全错误的结论，都值得单独记住。

坑一：git log -- .github 会骗你

直接对路径跑 git log，git 会做「历史简化」，在有 merge 的仓库里可能只留下极少数提交：

$ git log --oneline -- .github | wc -l
16      ← 假的

$ git log --full-history --no-merges --oneline -- .github | wc -l
251     ← 真的

差了 15 倍。而且被隐藏的恰恰是最有价值的部分——真正的结构性改动往往发生在被简化掉的分支上。任何对路径做的历史统计，都必须加 --full-history。

坑二：浅克隆会伪造一次「大爆炸提交」

调研开始时，我看到一个诡异的现象：99f6f02fec（2026-08-17）是一个没有父提交的提交，而且一次性新增了全部 27 个 .github 文件、+3981 行。看起来像是「公开发布时把内部历史压成了一个快照根」——一个很有故事性的解释。

它是错的。真相是本地这份 clone 是浅克隆：

$ git rev-parse --is-shallow-repository
true
$ cat .git/shallow
99f6f02fecdb7dff40c3fbc9470f5907c29f74ca

.git/shallow 里躺着的正是它。浅克隆边界上的提交在本地表现为无父提交，于是它相对于「虚无」的 diff 就是整棵树。git fetch --unshallow 之后，它恢复成一个普通的 merge 提交（rc.7 的发布合并），而且根本没碰过 .github：

$ git fetch --unshallow upstream
$ git show --stat 99f6f02fec -- .github
（无输出）

教训：在做任何 git 考古之前，先确认仓库不是浅克隆。否则你会围绕一个不存在的事件编出一整套解释——而且它听起来会很合理。

可复跑的核心命令

# 更新到最新并确保完整历史
git fetch upstream --prune && git fetch --unshallow upstream

# 真实的 .github 提交数与月度分布
git log --full-history --no-merges --format='%ad' --date=format:'%Y-%m' \
  -- .github | sort | uniq -c

# 逐文件：首次加入 / 末次改动 / 改动次数
for f in $(find .github -type f | sort); do
  echo "$f $(git log --full-history --no-merges --oneline -- $f | wc -l)"
done

# ci.yml 某个历史时点的行数与 job 清单
git show $(git rev-list -1 --before=2026-07-22 HEAD):.github/workflows/ci.yml \
  | grep -cE '^ [a-z][a-z0-9-]+:'

本报告的调研方式：12 个并行 agent 分别负责四个专题（ci.yml / 发布 / 专项验证 / 治理）、四个时期、Agent Note 挖掘、ci.yml 成长曲线，再由 2 个对抗性 agent 分别做事实证伪与完整性批评。事实核查改正了约 15 处（多为行号与 diff 数字），完整性批评贡献了 §10 的大部分内容——包括「公开仓上 CI 跑不起来」和「还有一套 GitLab CI」这两条，它们是单纯读 .github 永远发现不了的。

在你的规模上抄什么

这套 CI 的复杂度是被特定条件逼出来的：代码主要由 agent 写、有企业自建 runner 池、要发四条互不相关的产品线、跨三个操作系统。直接照抄大概率是负担。按规模拆开看：

一个人 + agent

  • 值得抄：all-checks-passed 汇总 job（含那个 always()）。十几行，让分支保护摆脱矩阵名字，以后加减 job 不用改设置。这是全篇性价比最高的一段。
  • 值得抄：CI 与本地钩子共用同一组 package.json 脚本。不要在 YAML 里写第二份命令清单——那是漂移的源头，这个仓库在 07-06 花了一整天才把它撤回来。
  • 值得抄：无密钥主 gate + 密钥单独成文件。即使你只有一个 API key，这个切分也让主 CI 在 fork 上能跑。
  • 值得抄：「跳过必须是可见的跳过」。如果你的测试会自跳过，就给它一个 preflight，缺条件时硬失败。这是最容易骗过自己的一类 bug。
  • 不用抄：failover 开关、串行跨平台参照、benchmark job、自建 runner。这些解的是「组织自有池会降级」和「优化后的清单可能漏跑」，你没有这些问题。

2–5 人

  • 值得抄：拆分理由写进文件头。sandbox.yml 第一句就解释了为什么它不在 ci.yml 里。半年后没人会记得，而 YAML 顶部的一句话比任何 wiki 都可靠。
  • 值得抄：把「阻塞 / 不阻塞」压缩成一次 needs 列表的取舍。并且不要用 continue-on-error——它把红变绿，等于让人学会忽略。要么进 needs，要么让它以独立 job 的身份红着。
  • 值得抄：改并发/拓扑之前先量。不需要 benchmark job，看一眼 Actions 里各 job 的实际耗时就够。这个仓库最贵的一课是：分片了 40 个 job，结果多数 gate 比 runner setup 还短。
  • 谨慎：标签分类法机器强制。规则本身很好（一个封闭的 kind/* + 一个开放的 area/*），但 706 行的策略引擎在这个规模是过度投资。先用 GitHub 自带的 required labels 或一个 20 行的脚本。

5–10+ 人

  • 值得抄：策略从默认分支检出。一旦接受外部 PR，「PR 不能改自己分支上的检查逻辑来豁免自己」就是必须的，而不是可选的。
  • 值得抄：发布 = 无凭据打包（每个 PR 都跑）+ 人工触发上传那批字节。把「能不能打包」和「要不要发布」彻底分开，发布环节不重新构建。
  • 值得抄：把 action 钉死在 SHA 上——而且要一致。这个仓库只钉了 3 处，最敏感的 PyPI publish 反而用了分支 ref，这是可以直接吸取的反面教材。
  • 值得抄：死代码要连注释一起删。那个躺了一个月的 if: false job 真正的危害不是浪费行数，而是有一条注释在声称一个已经不存在的缓存。
只因为 agent 写代码才存在的部分
