01 · 核心判断

它不是「带插件 API 的 agent」，是「跑在插件框架上的 agent」

绝大多数 harness 有一个特权内核，外加一圈扩展点。dsh 没有内核可打补丁： agent loop、会话日志、工具注册表、模型适配器，本身就是配置里可以卸载和替换的插件行。 dsh-base 这个基础 bundle 就是一次性插入的 78 行配置；web profile 再叠 51 行。

这句话很容易当口号听。判断它是不是真的，只需要看一件事：可替换性有没有兑现成删除量。本报告最有说服力的一处证据是 E2B 远程沙箱 —— 把整个执行世界搬到远端 Linux 沙箱，代价是禁用 2 行配置、插入 3 行配置，而 bash、PTY、LSP 三个消费方一行都不改、一个 fork 都不出 (见 第 4 节)。这是接缝设计能不能收敛的硬指标。

另一处是它对「真源」的处理。会话日志不是聊天记录的副产品，而是模型请求的唯一来源：每一次请求的消息数组都从日志重新投影出来，而不是在内存里累积。这条规则甚至有一个运行时断言在守(下一节会讲到它的一个重要限定)。

02 · packages/core · 13,462 行

一次 turn 的执行：声明式的骨架，可拦截的每一步

默认驱动器是 ReactLoopAgent，一共 496 行，位于 packages/core/agent-loop/src/agent.ts。它坐在一条只追加、序号连续的会话日志上。一个 step 是一次模型请求加上它触发的工具调用；一个 turn 是零个或多个 step。

日志里目前有 44 种会话事件类型，但只有 3 种会产生模型消息(user/message、assistant/message、tool/result)。这个 3 : 44 的比例是整套设计的支点：模型看得见的表面很窄，窄到可以被一条断言完整重算，而其余 41 种事件负责承载 UI、遥测、审批、计划、目标这些不进模型上下文的耐久事实。

压缩不删除

上下文压缩落地为 surfaceOp: replace —— 表面遮蔽掉一段区间，原始事件逐字留在日志里。于是「模型上下文」和「人类可读记录」变成同一条日志的两个投影，源码里因此专门存在一个 isAppendSurfaceEvent 谓词，并写明表面是渲染人类记录的错误来源：一次压缩会抹掉用户明明已经看过的对话。

重要限定

那条「模型可见 ⟺ 已落盘」的运行时断言，并没有挂在出厂的三个 bundle 里。我在 packages/bundle/{base,headless,web-app}/cordis.patch.yml 中检索dsh-invariants，零命中；真正挂载 InvariantRegistry 的是packages/examples/agent-spine-demo 与各包的测试拓扑。所以它是开发期、CI 与示例组合的保证，而不是用户跑 dsh --profile web 时在线上守着的东西 ——除非用户自己把它组合进去。这不影响架构价值，但影响你怎么向别人描述它。

03 · packages/boot · packages/bundle

组合：四层补丁，压平成一次调用

「可以从配置替换任何东西」这句话的兑现方式，是拒绝嵌套。profile、每个 bundle 的 cordis.patch.yml、home 级补丁、命令行 --patch，全部被拉平成一个补丁列表，由一次 applyEntryPatches 施加在空条目列表上。

配置里的 !!js 也不是模板语法，而是 with (ctx) { eval(expr) } 对活的插件上下文求值，且只在该条目声明的注入就绪之后才执行。这带来的表达力是真实的，风险也是真实的 —— 见 第 9 节 的 postmortem 0002。

04 · 26 个接缝 · 46 个 provider

能力接缝：三个角色缺一不是接缝

仓库把「可替换能力」定义成一个三角色结构，并在术语表里明确写死： Service Definition(拥有 ctx.<key> 与词汇类型)、Service Provider(一个或多个实现)、Consumer(注入者，通常是面向模型的工具)。只有一个角色不叫接缝。

接缝分两种机械形态，而且分法有依据： 16 个是抽象 Service 子类 —— 一个上下文只能有一个提供方，重复注册直接抛错，因为「有两个文件系统」本身就是组合错误； 10 个是并存注册表 —— 多个具名 provider 共存、按调用选择，因为「同时装 Exa、Perplexity 和 DeepSeek 三个搜索后端」正是它要的效果。

最能说明问题的是 ctx.fs 与 ctx.subprocess 这一对：它们合起来定义了一个「执行世界」。

沙箱那一层刻意做窄：ctx.sandbox 只做 argv 改写，策略(模式、工作区根)放在另一个服务ctx.sandboxPolicy 里 —— 就是为了防止一次性 shell、文件系统后端和 PTY 后端把自己关进三个不同的根目录。它的返回值也不是布尔：{argv, enforcement, denialSignatures, runnerFailureRules}，让消费方能区分「命令跑了、内核拒绝了写」和「启动器根本没起来」，而不必知道底下选了哪个后端。

平台沙箱实现形态
Linuxbwrap → Landlock降级链；Landlock 由一个自限制后 exec 的 C 启动器提供
macOSSeatbeltSBPL profile 由 writableRoots() 生成
WindowsACL 受限令牌是 sandbox-local 里的一级，不是独立 provider

Landlock 启动器有个值得一提的细节：它拒绝从元数据回答「Landlock 可用吗」，而是真的起一个短命子进程去建立并强制一套最大规则集 —— 因为 --version 式的探测在「有系统调用但拒绝强制」的内核上会误判为可用。

05 · packages/client · 71,896 行

浏览器里跑着第二棵 Cordis 插件树

这是整个仓库最被低估的部分。Web GUI 不是一个调 API 的 React 应用： packages/client/web/src/boot.tsx 里 new Context()，挂载同一份 vendored loader 源码，把一个浏览器模块系统注入 loader 的 internal 槽，然后对宿主推来的条目图逐行 loader.create()。

换句话说，Node 与浏览器两侧共用同一套 fiber 生命周期、inject 等待、ctx.effect 释放与 HMR,只换了一个 seam(EntryTree.import 的实现)。UI 组合走一个 API:ctx.slots.register()，声明一个子槽就是渲染它的授权 ——现行组合里有 42 个槽键、133 处注册。

Typert：把类型图当成编译产物发到浏览器

宿主服务上打 @Remote 的方法，在构建期被从 tsconfig.host.json 的ts.Program 里分析成类型图，按包发射成 lib/typert.remote-client.{js,d.ts}: Zod 编解码器 + 调用描述符 + declare module 合并。浏览器侧因此拿到的 ctx.remote.goals.create(...) 是真实的类型化方法，不是 Proxy。

这带来一个不寻常的约束

客户端程序在宿主编译完成前根本无法类型检查 ——所以 typecheck 脚本写成 build:lib:host && tsc -b tsconfig.client.json。线上契约不是一个手工维护的共享类型包，而是编译产物，且宿主是它唯一的权威。「做一个 shared-types 包」是显而易见的设计，这里被明确否掉了。

客户端与宿主的隔离靠两个永远无法合并的 TypeScript 程序(两边都增广同一批 cordis Context 键)，外加一个构建期纯度插件：任何跨插件的 @deepseek-ai/* 值导入直接抛错。十个平台模块按同一实例共享(React、cordis、ui-slots 等)，其余全部按 bundle 内联 ——这正是每个 UI 插件能独立热重载的原因。

06 · packages/subagent · 7 个 provider

把 Claude Code 和 Codex 当成可插拔的子 agent

SubagentProvider 只有三个方法(name / capabilities / start)，于是「委派给别家的 agent」成了一次普通的 provider 实现：

Provider驱动方式版本锁定
subagent-claude-code官方 @anthropic-ai/claude-agent-sdk0.3.220 / CLI 2.1.220

细节里有两处见功力。其一，Claude Code provider 让官方 SDK 拥有协议，却把 spawn 抢了过来：用 ManagedClaudeCodeProcess 包住 harness 自己的 SubprocessHandle 去满足Anthropic 的 SpawnedProcess 接口 —— 这样进程树权威留在 harness 手里，又不必 fork 别人的 SDK。

其二，四个跨进程 provider 全部声明 NO_START_CAPABILITIES，于是服务层直接拒绝 outputSchema / maxDepth / toolFilter / persona 请求，而不是收下再忽略。理由写得很清楚：接受并忽略会让同一个工具 schema 因为背后 provider 不同而含义不同。

对外还有另外两条：一个纯自动化的 ACP server，一个 3 请求 / 4 通知的 stdio JSON-RPC SDK 协议(Python SDK 说同一套协议)，以及作为 MCP 客户端的接入 —— 注意没有 MCP server。这些缺口被写在各包的 Known Limitations 里，没有藏。

07 · scripts/ · 124 个 .ts

62 道闸门：把每一条可机检的约定变成一个非零退出码

scripts/run-gates.ts 是一个会校验自身 DAG(重复 id、未知依赖、环)的小调度器，把 62 道唯一闸门组合成 14 个具名聚合：ci-primary 52 道、doc-sync 28 道、本地 check-all 46 道。

族它机械保证的东西
静态 / 类型typecheck、oxlint(规则集按 SHA-256 指纹钉死)、jscpd 克隆检测、knip
打包 / 产物publint、工作区约束、NodeNext 消费者类型检查、用纯 Node 导入构建产物验证不变量
文档7 个生成目录的 --check 新鲜度、JSDoc 覆盖、字数上限、双语配对、Mermaid 解析、Agent Note 格式
测试单测 + 每文件 100% 覆盖 + 真实 API e2e + 无密钥快照回放 + 浏览器快照

三个反常识的设计

一、覆盖率豁免不是豁免。 coverage-exempt 听起来像放过慢用例，实际做的是把它们拆到第二道闸门里照跑，只免掉 v8 插桩开销 —— 正确性信号一点没少。而且环境变量设成非 '1' 的值会抛错，而不是静默失效。

二、运行时不变量不是测试。 219 个包全部带一个 src/invariant.ts 伴生文件(35 个有可执行断言，184 个是空的、但必须写明 No runtime invariant: 的理由)。它们在每一次真实运行、每一次快照回放、每一个普通单测里在线断言事件流与可变数据之间的关系 ——这是类型和用例都覆盖不到的那一格。闸门强制那句解释，所以「空」不会烂成一次耸肩。

三、快照 fixture 是双向的。 同一份 session.jsonl 既是回放脚本又是期望输出。这消掉了通常的录制/断言不对称，但也带来一个 churn 问题，解法是一个相当深的stabilizeRefreshLog：在整条日志上建立规范化等价的字符串双射，尽可能复用已提交的 id、路径、时间戳，任何歧义就退回生成新值。没有它，每次刷新都会重写每一个 UUID。

为什么值得这么干?Agent Note 里说得很直白： 「这个代码库主要由编码 agent 开发。agent 遵守被强制的闸门远比遵守散文约定可靠，而当劳动由 agent 完成时，『工作量很大』不构成成本论据。」同一篇笔记也点名了这套体系自己的失效模式：100% 覆盖率的压力会催生没有断言的测试 ——并把变异测试列为计划中的对冲。

双语不是「翻译一下」：936 对文档由一份 .i18n.yaml 记录双方的 git blob 哈希加结构签名绑定。存 blob 而不是 commit 哈希是有用意的 —— 它让「上次确认过的原文」可被取回，于是不同步的一对变成一个三方 diff，可以按段落/表格行/列表项做最小改动更新，而不必整篇重译(重译会扔掉此前已被评审过的措辞)。

i18n 的 README 里还有一句罕见的自我限定：「闸门变绿只说明这一对在这个确切内容上被确认过一致，不说明那次确认是可靠的。」 所以 --write 拒绝裸跑，必须点名你确认了哪些 —— 让批量盖章成为一个可见的、刻意的动作。

09 · 尽调视角

账单记在哪里

以下每一条都有路径可查，并且我核对过数字。它们不否定上面的设计价值 ——它们是这套设计正在支付的代价，以及几处我认为需要盯住的地方。

值得盯vendored Cordis 已经变成一个 fork

vendor/ 里 9 个包、6,493 行，而 vendor/README.md 记录了18 处本地修改 —— 其中数处重写了 fiber 的释放语义、Loader/Include 的事务性回滚与配置解析，且各自点名了回归用例。这已经不是「钉住上游以便审计」，而是自己在维护一个 fork 并以自己的 scope 发到 npm。问题在于：没有任何机械手段可以从上游重建 vendor/，同步流程是「重新施加上面列出的本地修改」，即人工重新推导 18 段散文语义。而提议要验证这份漂移的那篇笔记，从 2026-06-11 起一直停在 proposed(当时只有 2 处修改)。vendor/README.md · .agents/notes/proposed/

已发生快照体系可以给自己的回归背书

Postmortem 0002：一个 disabled: !!js 表达式静默关掉了整个文件系统工具栈，横跨 8 个快照场景；所有闸门全绿，而快照刷新把坏掉的记录提交成了期望输出。因为期望输出是从实跑里重新录制的，确定性被当成了正确性。修复(在新鲜运行里拒绝 UNKNOWN_TOOL)补的是这一个症状 ——任何其他形式的静默降级组合，依然会产出一份自洽且通过的快照。docs/postmortem/0002

结构性贡献的最小单位是一个已发布的 npm 包

「一切皆插件」的成本不在运行时间接层，而在于：加一个哪怕不渲染任何东西的 React 占位，也要配 package.json、tsconfig、tsdown 配置、invariant 伴生文件、英文 README、中文 README、i18n sidecar、测试目录，再进三个目录。这笔固定税就是「一个目录选择器长成了 6 个包」的原因，并且它在结构上把团队推向拆分而不是合并。packages/host/directory-picker* · 2,844 行源码 + 3,691 行测试

校准问题抑制标记的数量，是闸门是否校准的诚实读数

631 处 v8 ignore 撑着 100% 覆盖率闸门， 492 处 jscpd:ignore 撑着克隆检测。这些豁免大多附有理由(这是好事)，但反过来说明：真实的工程精力正在被花在为满足阈值而撰写理由上。另外覆盖率的 v8 ignore 需附理由这条约定，目前只有文档、没有闸门，已有 15 处没写理由。vitest.config.ts · .jscpd.json

已漂移最该被读的那份文件，自己没有闸门守着

根 AGENTS.md 的仓库布局块是每个 agent 最先读的东西。我逐项比对过：它覆盖 49 个包组中的 32 个，漏掉 17 个 (包括 client/ —— 全仓最大的一组，71,896 行)，还列了 2 个已经不存在的组(self-modification/、support/)。原因很具体：verify-package-paths.ts 会扫这个文件，但解析不了这个代码块。37 道 verify-* 闸门全绿，而这份说明书三分之一过期。闸门在保护代码不被文档误导，没有保护文档不被代码甩下。AGENTS.md · scripts/verify-package-paths.ts

设计张力有些接缝在付抽象费、没收替换红利

subprocess、attachment、credentials、settings、lsp都是「定义包 + 唯一提供方」的拆分。更能说明问题的是反方向：subagent 接缝不得不在类型定义里暴露一个四布尔的能力矩阵和逐 provider 的散文说明，因为一个进程内 fiber 和一个跨进程 Codex CLI 本来就没在实现同一个操作。按仓库自己的规则(角色独立演进时才拆)，这更像是在提示它应该是两个接缝。

流程负载过程产物的增速快过产品消化它的能力

10 · 上手

两条上手路径，文档只清楚地讲了一条

路径做法成本
补丁 overlay dsh web --patch ./my.cordis.yml 挂一个树外插件 几分钟 · 零闸门
树内包 新建 packages/<group>/tool-foo 工作区包 约 20 个文件 · 一周量级

第一条是完整、受支持的扩展机制，并且真的能跑通。问题是没有任何文档告诉新人这一点 ——于是「加个工具」的任务会本能地走上第二条。而第二条的真正成本中心不是 TypeScript：一个新工具包会连带要求你手写 README.zh.md、Agent Note 的中文版，以及被你的包扰动到的 tool-catalog.zh.md / config-catalog.zh.md 等生成目录的中文对照，再重新记录每份 .i18n.yaml。

闸门本身的设计倒是相当体贴：几乎每道闸门都用 packages/*/* 通配而不是读注册表，所以新包自动进入约束、README 检查、config 目录、双语配对的作用域，不必编辑任何清单。两个例外(gen-tool-catalog.ts 的 TOOL_PACKAGES 和 packages/bundle/base)恰好就是新人会忘的两个，而它们的报错会直接点名文件和修法。

另外值得一提：生成目录质量很高，而且高得有道理。gen-tool-catalog.ts是在真实 Cordis 上下文里把每个工具插件启动起来再读 ctx.tools.schemas()，而不是解析源码 —— 因为 schema 可能来自加载期配置或运行时展开。它还双向设防：包不在清单里要报错，包启动了却没注册任何东西也要报错，并猜出最可能的原因(未满足的 inject)。读 docs/tool-catalog.md 比读 packages/ 更快也更可信。

11 · 方法

这份报告是怎么做的，以及它没做什么

13 个并行的分析 agent 分头深读源码(10 个按子系统，3 个分别扮演尽调、研究者、新人视角)，每条事实都要求给出打开过的文件路径。之后我复核了各 agent 之间互相冲突的数字，以本地实测为准—— 包括包组数(49，非 51)、ui-* 包数(31，非 45)、Agent Note 数(686)、vendor 修改数(18)、以及 AGENTS.md 布局块的逐项比对(覆盖 32、漏 17、多 2)。

未做的事

没有跑过任何构建、测试、闸门或产品二进制。所有行为性结论来自读源码、读类型、读用例断言与生成产物，而不是观察运行。尤其是：100% 覆盖率是 vitest.config.ts 里配置的阈值，不是我实测到的数字；三平台沙箱的内核行为、Claude Code / Codex 的真实 e2e(无密钥会自跳过)均未验证。行数一律是 wc -l 原始行数，含空行与注释 —— 这个仓库注释密度约 26%，所以绝对值偏高，但彼此之间可比。

分析过程中顺带发现几处文档漂移，已在上文对应位置标出： core/session 里写着「五种产生消息的事件类型」而实际是三种； capability-seams.md 里有已改名或不存在的包名； tool-catalog.md 声称 cordis 工具集「不在任何出厂树里」，但 apps/cli 的cordis preset 确实挂载了它；tool-cordis 的 README 落后于自己的源码一个版本模型。
